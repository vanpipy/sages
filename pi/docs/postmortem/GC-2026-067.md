# GC-2026-067 — Reminder chain closure

> **Date:** 2026-08-21
> **Status:** Resolved
> **Severity:** minor (operational gap, not a bug)

## What happened

After GC-2026-055 (auto-install routines) and GC-2026-060 (todo-reminder scaffold), the Sages reminder pipeline was **functionally complete** but **practically dormant**:

- `sages_reminder` tool: existed but had nothing to surface (no `audit-state-*.yaml`, no persisted todos).
- `sages-session-wrap` / `sages-resume` / `sages-watchdog` routines: auto-installed at session_start but the watchdog had no fingerprint to read (no audit-state) and the resume wrap had no completed tasks to summarize.
- `[sages session digest]` reminder: existed as a concept but had no upstream emission.

The practical symptom: the user (L3 orchestrator) ran GCs 044–066 over multiple sessions, but the reminder chain never fired any signal that wasn't manually emitted. The "watchdog stalls if no progress for 15+ min" behavior was theoretically live but observably dead.

## Root cause

Three independent upstream emitters in the L3 orchestrator pipeline were not wired:

1. **`pi/src/observability/runner.ts:emitRunEvent()`** (GC-2026-050 scaffold) — never called by `goal_contract_create` / `dag_synthesize` / `task_dispatch` / `orchestrator_audit`. Result: no `audit-state-{dag_id}.yaml` exists during workflow execution.
2. **`sages_todo({action: "sync"})`** — applied to in-memory state but did not call `saveTodoState()` before returning. Result: `todo-state.json` not persisted; `staleReminderFor()` has no accumulated signal to fire.
3. **Session-start reminder** — no module to format a digest of in-flight goals, pending verdicts, unmerged branches, and todo state.

The chain was 99% built but the last 1% of upstream wiring was missing. Without it, the watchdog, the digest, and the todo persistence all silently no-op'd.

## Fix

GC-2026-067 wired all three emitters in one batch (3 tasks, 4 commits, 1664 insertions):

A pre-existing catalog drift on `gate.json` (likely from GC-2026-051..053 era gate work that didn't regen) was discovered during audit and fixed in `e10579d` — orthogonal to the GC, but the audit caught it cleanly.

## Lessons

1. **Completion requires end-to-end smoke testing, not unit tests.** GC-2026-055 had unit tests for `sages_reminder` and a template-existence test for the routines. None of those tests would have caught the upstream wiring gap. The fix was discovered only because the user (L3) ran the tools manually after the merge and noticed "the watchdog has been alive for weeks but never fired any signal". Future audit templates should add an "end-to-end reminder-chain fire test" to the standard verify suite.

2. **Sub-agents have a tight turn budget on long DAG prompts.** Three of GC-2026-067's four sub-agent dispatches (T1, T2, T3) hit max-turns (61–73 turns / ~6–7 min) before committing. The prompts were 800–1500 words each, plus sub-agent spend on context exploration. The GC-2026-065 fix (deadline enforcement) correctly fires the cap, but the cap is too aggressive for the natural exploration phase. **Future sub-agent dispatch should** either (a) split each task into a smaller scope, or (b) pre-compute the answer (e.g. file paths, exact line numbers) in the orchestrator's prompt and hand the sub-agent a focused 200-word "do exactly this" brief. The orchestrator took over T1, T2, T3 directly and got them committed in 3 merges.

3. **Catalog drift hides in pre-existing typecheck noise.** The `gate.json` drift was only caught because T4 (auditor) explicitly ran `verify:catalog` as part of the standard gate bundle. Future audits should keep `verify:catalog` in the standard 5-gate bundle even when it "obviously passes" — drift is silent.

4. **`sages_todo` persistence was already wired in GC-2026-060 but never tested.** The fix in T3 was actually a test-only commit (6 tests added; the production code was already correct). This is the GC-2026-067 review-process working as designed — the T1/T2/T3 dev agents each ran the full `bun test` before committing, which caught the GC-2026-060 gap. **Future review templates should mandate: every claim of "production code is already correct" must be backed by a passing test in the same GC.**
