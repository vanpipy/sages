# GC-2026-068 — sages_todo owns the todo lifecycle, MC overlay driven by Sages

> **Date:** 2026-08-23
> **Status:** Resolved
> **Severity:** minor (architectural pivot, not a bug — superseded GC-2026-067 T3 follow-up)

## What happened

After GC-2026-060 (sages_todo persistence + todowrite mirror scaffold) and GC-2026-067 (reminder chain closure), the root todo store was being written by **two** paths:

1. **LLM direct call to `todowrite`** — Magic Context's built-in tool. Its `execute()` returns the echoed JSON without writing anywhere. A separate `capturePiTodowriteMessageIfCompatible` post-processor in `@cortexkit/pi-magic-context` scans `msg.content` for `toolCall.name === "todowrite"` and routes the args into `setTodoSnapshot` + `lastTodoState` for the terminal overlay.
2. **LLM call to `sages_todo({action: "sync"})`** — Sages' own tool. Writes to `TodoStateManager` + `todo-state.json` directly. The terminal overlay does NOT update from this path because Sages never calls `setTodoSnapshot`.

The practical symptom: when the LLM used `sages_todo sync` (which the soft-mode prompt recommends for >2-item workflows), the terminal overlay stayed blank or stale. Users had no live todo pane for the tool the system actually uses. Calling `todowrite` did work end-to-end, but `todowrite` was never the recommended path — and the soft-mode prompt was inconsistent (it said "todowrite" in the threshold reminder and "todowrite" again in the §Todo management text, while the actual tool the LLM was supposed to use was `sages_todo`).

GC-2026-067's postmortem had flagged GC-2026-068 as the planned follow-up: "migrate `extension.ts` tool_call handler at L320 from direct `todoState.apply` to the new `mirrorLlmTodoWriteToSages(items, todoState, { dagId })`". The investigation for that follow-up revealed the deeper issue: the **mirror architecture itself was wrong** — Sages was supposed to own the todo lifecycle, but it was only writing to its own store while MC's parallel `todowrite` path owned the overlay. Two writers, one rendered surface, no consistency guarantee.

## Root cause

The mirror module (`pi/src/tools/todo/todo-mirror.ts`) was a 200-line compromise designed to bridge two stores without resolving the ownership question:

1. **Dual ownership of `lastTodoState`.** Magic Context's `setTodoSnapshot(sessionId, todos)` is the only writer to the overlay's source-of-truth. Sages' `todoState.apply(items)` is the only writer to `todo-state.json`. The two stores were kept in sync only by the mirror's `mirrorLlmTodoWriteToSages` post-processor — which scanned the **LLM's todowrite tool calls**, not the Sages store. Any direct write to the Sages store (e.g. `dag_synthesize` → `deriveDagTodos` → `todoState.apply(derived)`) bypassed the overlay entirely.
2. **`todowrite` was not registered in the Sages tool list but appeared in the system prompt.** pi-coding-agent itself does NOT ship a `todowrite` tool (verified by searching `createAllToolDefinitions` in `pi-mono/packages/coding-agent/src/core/tools/index.ts` — only `read` / `bash` / `edit` / `write` / `grep` / `find` / `ls`). The `todowrite` tool was registered exclusively by `@cortexkit/pi-magic-context`. So in a Sages session, the LLM could call `todowrite` only because MC registered it; if MC were disabled (the official escape hatch per MC's own config docs), the LLM would see no todo tool at all. This was an unnecessary dependency on MC for LLM-facing surface.
3. **The 5-step workflow crossed the abstraction boundary unnecessarily.** LLM → `todowrite` → MC capture → `setTodoSnapshot` → overlay.update was 4 hops for a single intent. Sages directly writing its own store and then calling `setTodoSnapshot` is 1 hop from Sages' perspective, with the overlay update as a single optional side-effect.

## Fix

Replace the mirror architecture with direct Sages ownership. Sages writes to its own store, then optionally notifies the Magic Context overlay via the same `setTodoSnapshot` API MC itself uses. MC's `todowrite` tool is disabled so the LLM tool surface shows only `sages_todo`. MC's overlay widget remains active so the user keeps the live todo pane.

One commit, single batch (no DAG dispatch — the work is small enough for the main agent to handle directly under soft mode, per the `dag_threshold: 2` recommendation):

## Follow-ups

1. **Verify `setTodoSnapshot` API stability on MC upgrades.** Sages' dynamic-import probe catches the absent-package case but not the case where MC renames or reshapes the function. Add a smoke test to `pi/test/tools/todo/` that mocks the import and asserts `notifyOverlay` does not throw when MC's API moves. Trigger: `@cortexkit/pi-magic-context` version bump above 0.36.1.

2. **Long-term: consider removing the MC overlay dependency entirely.** The overlay is a nice-to-have for the terminal pane, but `todo-state.json` + `before_agent_start` already give the LLM the same surface in its system prompt. If MC's overlay proves unstable or starts conflicting with other UI layers, the cleanest fallback is "no overlay; LLM reads it from `[sages todos: ...]` every turn". Document this as an opt-out flag in `~/.config/cortexkit/magic-context.jsonc` (`todowrite.overlay: false` already works today — verify the rest of Sages degrades cleanly).

3. **Pre-existing bug from GC-2026-067 follow-up #3 still applies.** `pi/scripts/verify-gcdb.ts` hardcodes `PI_ROOT = resolve(__dirname, "..")` so it reads from `pi/.pi/orchestrator/` instead of the repo root. Same fix shape: walk one more `..`.

## Lessons

1. **Investigate the abstraction boundary before adding a bridge.** GC-2026-067 added `todo-mirror.ts` to bridge two stores without questioning whether two stores should exist. The bridge worked in unit tests (21 tests added in GC-2026-067 T3 all passed) but masked the deeper architectural smell — dual ownership of the same surface. **Future mirrors / shims / adapter modules should require an explicit "why two sources of truth?" comment in the module header, and the answer needs to survive a 30-second review from the L3 orchestrator.**

2. **MC's own config docs already documented the right escape hatch.** `@cortexkit/pi-magic-context` schema line for `todowrite.enabled`: *"Pi only: register Magic Context's todowrite task-list tool. Disable if you use your own todo extension."* We were not using our own todo extension — we were sharing one. The pivot to "fully own it" is the canonical answer the config was pointing at. **Future integration with shared tools should grep the upstream config schema for the disable-before-rewriting escape hatch before writing glue code.**

3. **`todowrite` was never registered by pi-coding-agent itself** — only by MC. The system prompt listed `todowrite` because MC registered it; pi's own `createAllToolDefinitions` returns only the seven core tools (read/bash/edit/write/grep/find/ls). **Future audits of "what tools does the LLM see?" should check `createAllToolDefinitions` first, then layer the optional registrations on top, rather than assuming system-prompt listings are ground truth.**

4. **The soft-mode prompt drift ("todowrite" → "todo list" → "sages_todo") was the actual user-visible symptom.** Once the user typed `sages_todo` in the LLM UI, no overlay updated. Once the user typed `todowrite`, the overlay updated but the Sages store stayed stale. The fix is single-source-of-truth (Sages owns everything; overlay is a downstream view). **Future work that splits a surface across two owners should add a "what does the user see vs what does the LLM see" checklist to the design phase.**

5. **Catalog regeneration caught a stale `gate.json` (still from GC-2026-051 era).** The catalog verifier runs as part of `check:all` and flagged it. This is exactly the lesson from GC-2026-067's "catalog drift hides in pre-existing typecheck noise" — keeping `verify:catalog` in the standard 5-gate bundle paid off again.
