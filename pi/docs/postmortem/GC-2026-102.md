# GC-2026-102 — Postmortem

## What happened

Two workflow_run gaps closed. Both were postmortem-flagged follow-ups
that had been left open because of scope ambiguity; this GC commits
to specific semantics for each.

| # | Item | Status |
|---|---|---|
| R-INT | End-to-end integration test (real subscribeWorkflow + real-format spawn ids + real workflow:phase-complete events) | NEW — `test/tools/orchestrator/workflow-run-integration.test.ts`, 3 cases |
| V5 | NEEDS_CLARIFICATION resume pathway (workflow-run reads `options.clarification_answer` + previous state) | NEW — `workflow-run.ts` `loadWorkflowState` + `buildResumeOutput` |
| V4 | `agent_overrides.fix` → DEVELOPER_FIX_PROMPT selection | ALREADY DONE in `workflow-graph.ts:400` (`agentType: "Fix"`) — Batch C's postmortem noted this was done but the orchestrator's `agent_overrides` parameter is still dead surface. Cleanup of the dead surface is deferred. |

## Root cause

R-INT — The existing test suite (`workflow-run.test.ts`, 15 cases)
covered orchestrator-internal phase aggregation but did NOT exercise
the production wiring. Every test used a local `makeHarness()`
with a fake `pi.events` bus and a `subscribeWorkflow` RE-IMPLEMENTATION
in test code. The cascade-agentid postmortem (GC-2026-pi-tasks-cascade-agentid)
noted that the unit tests' synthetic id shape (`agent-${task.id}`)
masked the pre-registration bug. A test that drives the real
`subscribeWorkflow` + real-format ids would have caught the bug.

V5 — `workflow-run.ts` records `clarification_answer` into
`workflow-{goal_id}.yaml` on the needs_clarification path but never
reads it back. The user answer was archived but the cascade didn't
auto-resume. Workflow-worktree-namespace postmortem F5 flagged this
as a follow-up.

## Fix

### 1. R-INT — `test/tools/orchestrator/workflow-run-integration.test.ts` (NEW, 3 cases)

Three test cases drive the production wiring through a fake `pi.events`
bus. The mock subagent layer returns `randomUUID().slice(0, 17)` ids
(matching `pi-subagents/agent-manager.ts:346`) so the cascade-agentid
shape mismatch cannot hide behind synthetic ids.

- **Happy-path 5-spawn workflow** (`max_fix_iterations: 3`):
  Implement → Review_1 → Review_2 → Review_3 → Merge (5 primary spawns)
  plus 4 advisor spawns (1 DeveloperAdvisor + 3 ReviewerAdvisor).
  Asserts every spawn id is real-format, the workflow:start payload
  shape matches `WorkflowStartPayload`, and 5 `workflow:phase-complete`
  events fire with verdict=CLEAN.

- **NEEDS_CLARIFICATION pause + resume**: drives a paused run, then
  re-dispatches with `clarification_answer`. Asserts the resume pathway
  records the answer and returns `status: "success"` with
  `clarification_answer_recorded` echoed.

- **NEEDS_CLARIFICATION pause + no answer (re-dispatch without
  `clarification_answer`)**: asserts the resume pathway does NOT fire
  (the state file is overwritten with `status: pending` for the fresh
  run, NOT `needs_clarification_answered`).


What the resume pathway does:
- Loads the existing `workflow-{goal_id}.yaml`
- Records the user's `clarification_answer`
- Updates the state file's `status` to `needs_clarification_answered`
- Returns `WorkflowRunOutput` with `status: "success"` and
  `clarification_answer_recorded` echoed so the orchestrator main
  agent can confirm the recording succeeded

What it does NOT do (deliberate):
- It does NOT re-trigger pi-tasks's cascade. The cascade in
  pi-tasks's `subscribeWorkflow` pauses on `NEEDS_CLARIFICATION` and
  has no internal "pick up" pathway. Adding one would require
  pi-tasks changes (excluded from this GC). The orchestrator main
  agent must re-dispatch a fresh `workflow_run` with the clarified
  goal in scope.
- It does NOT advance the existing TaskStore's paused Review. The
  fresh run builds a NEW static graph; old tasks remain in the store
  as historical state.

The pre-flight check (`loadWorkflowState`) is intentionally narrow:
it only parses the keys the resume pathway needs (`status`,
`clarification_answer`). Anything else falls through to `undefined`
and the caller treats it as "no prior run" — same as if the file
didn't exist.

## Behavior change (deliberate)

Three behavior changes, all minimal:

1. **New resume pathway**: when `options.clarification_answer` is provided
   AND the previous run paused on `NEEDS_CLARIFICATION`, the workflow
   resolves with `status: "success"` and the answer echoed back.
   Without one of those conditions, behavior is unchanged.

2. **New state-file value**: `status: "needs_clarification_answered"` —
   added to the type union. The state-file saver also gains a
   `clarification_answer: <answer>` line when the field is set. New
   state files include these; old state files are unaffected (the
   loader handles missing keys as `undefined`).

3. **Integration test surface**: 3 new test cases. No source change
   beyond the test file.

## Lessons

1. **The integration test would have caught the cascade-agentid bug.**
   The 2 real-format-id integration tests (happy-path + NEEDS_CLARIFICATION
   pause) would have failed loudly if the bug were still present:
   pi-tasks's `subscribeWorkflow` with real-format spawn ids triggers
   the cascade-agentid regression check by surface. The synthetic-id
   unit tests in `path-b-e2e.test.ts` had the right shape but only
   ran in isolation; the integration test exercises the
   `workflow_run → subscribeWorkflow` boundary directly.

2. **Driving async cascades from tests is hard.** The integration test
   required multiple `await flush()` between each `completeNext` call
   to let pi-tasks's async cascade drain. One `setImmediate` was
   sometimes insufficient; two sufficed. The harness tracks
   `completedIds` (a Set) so `completeNext` finds the NEXT un-completed
   agent of the requested type rather than re-completing the first
   one. The `completeByIndex(idx)` helper is provided for tests that
   want explicit positional control (the happy-path uses this).

3. **`loadWorkflowState` returns undefined on malformed state, not
   throws.** The narrow parser catches missing files, unreadable files,
   and missing keys — all collapse to "no prior run". This is
   important because the resume pathway runs BEFORE the goal
   contract is validated; if state loading throws, the fresh run
   would be blocked by a stale workflow-{id}.yaml.

4. **V4 is partly done and partly dead.** `pi-tasks/src/workflow-graph.ts:400`
   dispatches `agentType: "Fix"` which maps to FIX_AGENT using
   DEVELOPER_FIX_PROMPT — that part is correct. The orchestrator's
   `agent_overrides.fix` parameter is still dead surface (declared
   in the type schema, never read by the runtime). Cleaning up the
   dead surface is a Batch C-style task; deferred.
