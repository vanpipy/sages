# GC-2026-088 — Postmortem (post-hoc reconstruction)

## What happened

`pi-orchestrator/scripts/verify-catalog.ts` and `verify-gcdb.ts` used a
shared `PI_ROOT` constant pointing at the package root
(`pi-orchestrator/`). But the institutional docs (`gc-index.md`,
`postmortem/`) live one level up at `<repo>/pi/docs/`, and orchestrator
state lives at `<repo>/.pi/orchestrator/`. The verifiers had been
walking the wrong tree — claiming "all GCs covered" against a phantom
postmortem directory while real postmortems went uncovered.

## Root cause

`PI_ROOT` was set to the package root in the very first commit
(`pi-orchestrator/scripts/verify-catalog.ts`). The verifier was
self-validating: it checked a directory that was convenient to reach
(`pi-orchestrator/.pi/orchestrator/` did not exist either, so the
verifier trivially returned "OK — no goal contracts"). This silently
masked the institutional coverage problem for several GCs.

## Fix

Commit `712f899 fix(pi-orchestrator): verifier path offset —
institutional coverage now real` rewrote the path resolution:

- `PI_ROOT` derived from `import.meta.url` walks **up one level**
  to `<repo>/`, so institutional docs (`<repo>/pi/docs/`) and
  orchestrator state (`<repo>/.pi/orchestrator/`) resolve correctly.
- Both `verify-catalog.ts` and `verify-gcdb.ts` updated to the new
  resolution.

This GC unblocked every subsequent GC's institutional coverage (a
postmortem written for a previous GC now correctly attaches to that
governance's id, and the verifier can find it).

## Verification

The verifier was extended to print a count of checked + uncovered GCs.
After this fix, the baseline number of uncovered GCs was non-zero for
the first time, exposing the coverage drift that had been silent.
