## What happened

Post-FU3 audit of the unified task-feeder (GC-2026-108 + GC-2026-113
+ GC-2026-114) found two real issues. The first is a subtle race
condition that makes the workflow-handler's prior-Review summary
injection dead code; the second is a TaskUpdate race that can
cause "No background process for task N" errors in the LLM-facing
tool surface.

### Issue 1 (HIGH) — cascadeSpawn registered-listener race

The unified task-feeder is registered in `pi-tasks/src/index.ts`
at line 237, BEFORE the workflow-handler's `subscribeWorkflow` at
line 297. When `subagents:completed` fires, the event bus calls
the feeder's listener FIRST, then the workflow-handler's listener.

The feeder's listener runs `cascadeSpawn` (line 142-157 of
`task-feeder.ts`), which walks the store for pending feedable
tasks. For a typical workflow, this finds the next Review or
Fix-i task (e.g. Review_2 waiting for Fix_1) and spawns it via
`maybeAutoSpawn(t)`. The task's status flips to `in_progress`.

Then the workflow-handler's listener runs. Its `onSubagentCompleted`
calls `dispatchFixForReview` (if a Review NEEDS_WORK) which creates
Fix_1, then runs its own cascade loop. The loop checks each
pending task and tries to inject the prior-Review summary BEFORE
calling `feed.maybeAutoSpawn(t)`. But the Review_2 task is
already `in_progress` (spawned by the feeder), so the workflow-
handler's loop SKIPS it. The summary never gets injected.

**Fix**: `cascadeSpawn` now skips tasks with
`metadata.workflow_run_goal_id` set. The split is clean: feeder
cascades user / decompose tasks; workflow-handler.ts's own
cascade loop (which walks pending tasks and injects the summary
before calling `feed.maybeAutoSpawn(t)`) handles workflow tasks.
The pre-existing `prior review summary` tests in
`workflow-handler.test.ts` (Review_2, Review_3, etc.) still pass,
which proves the fix is correct.

### Issue 2 (MEDIUM) — TaskUpdate void race

`TaskUpdate` (line 1045) used `void feeder.maybeAutoSpawn(task)` to
fire the spawn. The other 4 producers (`TaskCreate` LLM, `/tasks
create` slash, `TaskExecute`, `materializeDecomposeChain`) all use
`await`. The race: if the LLM called `TaskUpdate({ agentType: "X" })`
to activate a previously-manual task, then immediately called
`TaskOutput({ task_id })`, the spawn hadn't completed yet (the
tool returned immediately). `TaskOutput` reads `task.owner` and
errors with "No background process for task N" if it's undefined.

**Fix**: change `void` to `await`, and make `execute` an
`async execute` (matches TaskCreate's pattern from GC-2026-113
FU0 Phase 2b). The tool now waits for the spawn RPC to return
before resolving.

## What did NOT change

- `pi-tasks/src/workflow-handler.ts` is unchanged. The cascade
  loop + prior-Review summary injection was always correct; it
  was just being bypassed by the feeder's earlier spawn.
- `pi-tasks/src/index.ts` TaskUpdate body is otherwise unchanged
  except for the `void` → `await` swap and the `async execute`
  signature.

## Follow-ups

- **The dispatchAdvisorForTask comment** (workflow-handler.ts:553)
  is misleading (says "the next cascade scan tick picks this up
  automatically" — actually the workflow-handler's own cascade loop
  picks it up because the feeder's cascade now skips workflow
  tasks). LOW priority follow-up; update the comment.
- **The feeder no longer cascades workflow tasks.** If a future
  feature wants to add non-workflow-handler dispatch paths for
  workflow tasks (e.g. a debug override), the filter at line
  `cascadeSpawn` would need to be revisited. Filed as NIT.
- **FU2** (filed earlier): persist `agentTaskMap` across session
  restarts. Unchanged.
