## What happened

GC-2026-118 F4 centralized the cross-package channels between **pi-orchestrator** and **pi-tasks** (`workflow:start`, `workflow:phase-complete`, `tasks:rpc:decompose-materialize`) in a new `pi-tasks/src/event-channels.ts`. F4 explicitly deferred the `subagents:*` channels owned by `pi-subagents` because centralizing them in `pi-tasks` would have inverted ownership (`pi-tasks` would own channel names that `pi-subagents` emits).

This GC completes the picture: the `subagents:*` channels are now centralized in a new `pi-subagents/src/event-channels.ts` (where the owner lives).

## Channels centralized

**Lifecycle** (12):

- `subagents:started` — emitted when an agent process begins (after spawn RPC resolves)
- `subagents:completed` — emitted on successful terminal state
- `subagents:failed` — emitted on agent failure (genuine error path, distinct from `parent_aborted`)
- `subagents:parent_aborted` — emitted when the orchestrator session aborts (intentional stop)
- `subagents:compacted` — emitted after a context-compaction pass within the agent loop
- `subagents:created` — emitted when a subagent record is created (before spawn)
- `subagents:steered` — emitted when a steer message is injected into a running agent
- `subagents:scheduled` — emitted when a subagent is scheduled for future execution
- `subagents:ready` — broadcast on `session_start` once the runtime is initialized
- `subagents:scheduler_ready` — emitted when the scheduler sub-component is ready
- `subagents:settings_loaded` — emitted when persisted settings are loaded
- `subagents:settings_changed` — emitted when settings change mid-session

**RPC** (4):

- `subagents:rpc:ping` — version-protocol ping
- `subagents:rpc:spawn` — agent spawn RPC (returns `agentId`)
- `subagents:rpc:stop` — agent stop RPC (returns success bool)
- `subagents:rpc:consume` — internal — caller asks the runtime to consume + drop a subagent's result

A new helper `rpcReply(channel, requestId)` composes the templated `subagents:rpc:*:reply:${requestId}` names from a base channel + request id (the templating happens at call site, so a constant would not capture the dynamic part).

## Fix

### New file: `pi-subagents/src/event-channels.ts`

Owns the 16 `subagents:*` channel constants (12 lifecycle + 4 RPC) + the `rpcReply()` helper. All emit / handleRpc sites inside `pi-subagents` now reference these constants instead of string literals.

### Consumers updated

| file | sites | what |
|---|---|---|
| `pi-subagents/src/settings.ts` | 2 | `emit(SUBAGENTS_SETTINGS_LOADED \| SUBAGENTS_SETTINGS_CHANGED, ...)` |
| `pi-subagents/src/schedule.ts` | 1 | `emit(SUBAGENTS_SCHEDULED, ...)` |
| `pi-subagents/src/cross-extension-rpc.ts` | 3 | `handleRpc(events, SUBAGENTS_RPC_PING \| SUBAGENTS_RPC_SPAWN \| SUBAGENTS_RPC_STOP, ...)` |
| `pi-subagents/src/index.ts` | 11 | `emit(SUBAGENTS_*, ...)` for 9 distinct channels (one is double-issued) |

### Cross-package import policy (deliberately asymmetric)

- **pi-orchestrator → pi-tasks**: pi-orchestrator imports from `@sages/pi-tasks/event-channels` (the F4 pattern; pi-orchestrator already depends on pi-tasks per `package.json`).
- **pi-tasks → pi-subagents**: pi-tasks does **not** import from `@sages/pi-subagents/event-channels`. pi-tasks is a peer of pi-subagents (both extend pi, communicate only via the event bus) and has no compile-time dep on it. The `subagents:*` strings in `pi-tasks/src/*.ts` mirror the canonical constants verbatim.

The asymmetry is intentional. `pi-subagents` is the runtime (it owns the channels); `pi-tasks` is a peer that consumes events. Adding a dep just to share string literals would invert the boundary architecture (event-bus peers should not import each other). Drift is caught indirectly: if pi-subagents ever renames a channel, the pi-subagents vitest suite catches the source-of-truth change; pi-tasks's listeners then fail at runtime when their channels go silent, prompting the rename.

The `pi-tasks/src/event-channels.ts` header comment was updated to document this peer boundary policy explicitly (replacing the F4-era "centralizing them here would invert the ownership" wording).

### Out of scope

- `subagents:rpc:ping:reply:${requestId}` (and other `:reply:` RPC reply channels) — templated by request id; handled by `rpcReply()` helper.
- `subagents:record` — `pi.appendEntry` channel (host log), not an event channel.

## What did NOT change

- The peer/event-bus boundary between pi-tasks and pi-subagents. pi-tasks still uses string literals to listen; pi-subagents uses imported constants to emit. The boundary is the same shape — only spelling consistency improved.
- The `subagents:rpc:*` request/reply protocol shape. `rpcReply()` is a helper for the consumer side; producers still emit the literal channel name (e.g. `pi.events.emit(SUBAGENTS_RPC_PING, ...)`).
- Any consumer outside `pi-subagents/`. pi-orchestrator does not consume `subagents:*` channels directly (it goes through `Agent` / `get_subagent_result` / `steer_subagent`, which delegate to the runtime).

## Follow-ups

- **Future cross-package dep if the boundary architecture changes** — if pi-tasks ever depends on pi-subagents (e.g. for shared types beyond channels), the canonical constants would migrate to be imported directly. Today's peer-only architecture makes that premature.
- **Schema versioning for `subagents:*` event payloads** — F4 deferred `workflow:phase-complete` schema versioning; the same applies here. The `subagents:started` / `subagents:completed` / `subagents:failed` payloads are inline types in `event-channels.ts` consumers (comments describe fields). A future GC could define them as explicit types — defer until a concrete motivation.
- **`subagents:settings_loaded` / `subagents:settings_changed` RPC unification** — currently settings events are emitted but no consumer outside pi-subagents listens (per recon). If pi-evaluator or other packages start consuming them, a typed payload schema would be needed.
