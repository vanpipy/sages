# GC-2026-090 — Postmortem (post-hoc reconstruction)

## What happened

GC-2026-089 wrapped 8 orchestrator tools in identical try/catch +
`Content[%]` boilerplate, scattered across 5 source files.
`f8a73b9 refactor(pi-orchestrator): extract wrapRegisteredTool helper,
eliminate 8-file copy-paste` collapsed that copy-paste into a single
helper module.

## Root cause

The defensive wrapper was applied per tool to be cautious to be the
fastest path to fix the renderer crash (GC-2026-089). That pragmatic
choice left 8 copies of the same boilerplate. Each new tool author
had to remember the wrapper — a maintenance trap that had already
caught the project twice (todowrite tools in GC-2026-085, then the
8 surface tools in GC-2026-089).

## Fix

`pi-orchestrator/src/registered-tool-wrapper.ts` (new) — a single helper
`wrapRegisteredTool<TParams, TResult>(toolName, execute)` that:

1. Awaits the execute call (so async resolves before JSON.stringify).
2. Pass-through if `Array.isArray(result.content)` (legacy ToolResult
   callers).
3. Otherwise wraps in
   `{ content: [{ type: "text", text: JSON.stringify(result, null, 2) }],
   details: result }`.
4. On exception: structured error block with `{ status: "error", error: message }`.

The 5 source files that previously hand-wrapped their execute
results now use the helper. Each `registerTool` call becomes a
one-liner.

## Verification

`pi-orchestrator/test/registered-tool-wrapper.test.ts` (new) covers
all 4 semantics. The post-refactor orchestrator's `registerTool` calls
are uniformly a single helper invocation; adding a new tool cannot
forget the wrapper.
