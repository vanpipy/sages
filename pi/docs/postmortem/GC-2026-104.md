# GC-2026-104 — Postmortem

## What happened

Removed the `dag_id` compat shim that `GC-2026-path-B-field-renames`
added when it renamed `ManagedWorktreeRequest.dag_id` → `goal_id`.
The shim was explicitly marked for removal in the next release
("removed in the next release" in the schema description); that
release has now shipped.

## Root cause

`GC-2026-path-B-field-renames` (merged 2026-10-01) renamed
`ManagedWorktreeRequest.dag_id` → `goal_id` and added a one-release
compat shim so callers using the old field name wouldn't break.
The shim was tagged for removal in the follow-up GC. Batch B / D /
E of this cleanup run didn't touch it (Batch B renamed the verify
regex but not the parser). Batch F's G1+G2 closes that loop.

## Fix

### 1. `pi-subagents/src/worktree-contract.ts` (parser)

- `ManagedWorktreeRequest.dag_id?: string` field removed
- TypeBox schema's `dag_id: Type.Optional(...)` field removed
- Parser's `has_dag_id` / `obj.dag_id` reads removed
- The `accept goal_id OR dag_id, but not both` dual-field error message
  replaced with a simpler `goal_id must be a non-empty string` message
- Schema description updated to remove the dag_id references

### 2. `pi-subagents/src/agent-manager.ts` (doc comments)

- Two JSDoc comments that referenced the dag_id field alias updated to
  say `goal_id`.

### 3. `pi-subagents/src/invocation-config.ts` (doc strings)

- Five references to `{ dag_id, task_id, ... }` updated to
  `{ goal_id, task_id, ... }`.

### 4. `pi-subagents/src/agent-prompts/{developer,merger}.ts` (doc comments)

- Historical reference in `developer.ts` (removed `todowrite_compile /
  todowrite_progress` tools once took a `dag_id`) — kept as
  historical context; doesn't reference the worktree-contract field.
- `merger.ts` audit file name doc updated from `dag_id` to `goal_id`.

### 5. Top-level doc + verifier updates

- `AGENTS.md`: managed-worktree example updated from `{ dag_id, ... }`
  to `{ goal_id, ... }`.
- `pi-orchestrator/scripts/verify-isolation-modes.ts`: example shapes
  in the doc comment updated.
- `pi-orchestrator/skills/orchestrator/SKILL.md`: dispatch table
  examples updated.

## Behavior change (deliberate)

Callers that pass `isolation: { dag_id: "GC-..." }` to the Agent
tool now get a parse error (the canonical field is now `goal_id`).
The parser previously accepted either name; now it only accepts
`goal_id`. This is the documented removal contract from
`GC-2026-path-B-field-renames` ("removed in the next release").

## Lessons

1. **Dead-surface cleanup is iterative.** The original `dag_id` →
   `goal_id` rename in Batch C / D / E didn't touch the parser's
   fallback path — the shim was documented for removal but nobody
   removed it. This GC closes that loop. Future renames should
   consider: "what was the explicit 'removed in next release' marker?"
   and target it specifically.

2. **The drift-sweep postmortem had KEPT `dag_id` deliberately.** The
   `pi/docs/postmortem/GC-2026-evaluator-drift-sweep.md` postmortem
   says:
   > "The `pi-evaluator/src/extension.ts` `dag_id` back-compat alias
   > (from `GC-2026-evaluator-drift-sweep`) is intentional (test
   > fixtures pre-dating the rename use the old name). KEPT."
   This GC deliberately did NOT touch pi-evaluator — that's a separate
   concern. The scope is strictly pi-subagents.

3. **Parser narrowing doesn't break test fixtures when the fixture
   already uses the canonical name.** The worktree-contract test
   suite (33 tests) uses `goal_id` exclusively; removing the `dag_id`
   fallback had zero test impact.

## Follow-ups

- None from this GC. The compat shim is fully removed.
