## What happened

GC-2026-108 Phase 1 shipped the unified task-feeder module
(`pi-tasks/src/task-feeder.ts`) + 24 unit tests. The producer
refactor (5 producers + 3 legacy listeners + `cfg.autoCascade`
gate) was deferred to "Phase 2" because it breaks 60+ existing test
fixtures that assume the legacy `TaskCreate + TaskExecute`
two-step pattern.

GC-2026-111 attempted the full Phase 2 refactor in one GC. The
producer-side changes (`pi-tasks/src/index.ts`) mechanically
worked — the unified feeder correctly handles the
`TaskCreate + agentType → auto-spawn → workflow:phase-complete
cascade` flow that previously required a separate `TaskExecute`
call. The wiring (replacing the 3 legacy listeners with
`registerTaskFeeder`, threading `feeder.maybeAutoSpawn` into
`TaskCreate` / `/tasks create` / `TaskUpdate` / `TaskExecute` /
`materializeDecomposeChain`) is straightforward.

What broke is the test surface: **40 of 60+ test fixtures assume
the legacy two-step pattern**. The new model auto-spawns on
`TaskCreate`, so the followup `TaskExecute` in the fixtures
errors with "not pending". The fixtures are spread across:
- `pi-tasks/test/subagent-integration.test.ts` (~30 fixtures)
- `pi-tasks/test/agent-reattach.test.ts` (~6 fixtures)
- `pi-tasks/test/task-execute-spawn-options.test.ts` (~3 fixtures)
- `pi-tasks/test/subagent-result-consumption.test.ts` (~6 fixtures)
- A few path-b-e2e / workflow-handler fixtures

These fixtures need to be updated to match the new model. The
update is mechanical (remove the `TaskExecute` followup, or use
`feeder.maybeAutoSpawn` directly in the test), but it's 60+ files
of edits. Doing it in this session without a subagent-dispatch-capable
session (this session has no `pi-tasks` / `pi-subagents` extensions
registered per FU1a) is too risky — the test count drift is too
high to validate manually.

GC-2026-111 was therefore **reframed mid-GC to ship zero code**:
the `pi-tasks/src/index.ts` changes were reverted. The actual
Phase 2 work is deferred to **two focused follow-up GCs**:

- **GC-2026-112 (Phase 2a — test fixtures)**: update 60+ test
  fixtures to the new "TaskCreate auto-spawns" model. Mechanical
  but large. No behavior change in production code; the
  fixtures just stop assuming `TaskExecute` follows every
  `TaskCreate`. This GC can be reviewed in isolation.

- **GC-2026-113 (Phase 2b — producer refactor)**: wire
  `feeder.maybeAutoSpawn` into 5 producers; remove the 3 legacy
  cascade listeners; remove `cfg.autoCascade`. Pure code refactor.
  Once GC-2026-112's fixtures are updated, this refactor will
  pass tests without further fixture work.

## Why this design

Doing both in one GC was the original plan. Splitting into two
follow-ups is the right move when:
- the work is too large to validate in one session without
  subagent dispatch
- the two halves have a clean dependency order (test fixtures
  first, then producer refactor)
- the test-fixture GC is reviewable in isolation (it's just
  "delete the followup `TaskExecute` calls; the auto-spawned
  task is already in_progress")

The split also gives the maintainer a clean revert path: if
GC-2026-113's refactor turns out to have a subtle behavior
change, the existing tests (post-112) will catch it precisely
because the new tests assert the new behavior.

## What broke / what we had to fix mid-implementation

- **The mechanical refactor works.** The unified feeder correctly
  handles all 5 producer paths. The wiring is straightforward
  (replace listeners, add `feeder.maybeAutoSpawn` to 5 sites,
  remove `cascadeConfig` + `cfg.autoCascade`).
- **The test surface doesn't.** 40 fixtures assume the legacy
  `TaskCreate + TaskExecute` two-step. Updating them in the same
  GC inflates the diff to "one refactor + 60 file edits" — too
  much for one review.
