# GC-2026-086 — Expose aft_* + ctx_* tools in the orchestrator active toolset

## What happened

`pi-orchestrator/src/extension.ts:175-181` (the `session_start` hook) called
`pi.setActiveTools([...ORCHESTRATOR_TOOLS, ...SUBAGENT_TOOLS, ...BASELINE_TOOLS, ...TODOWRITE_TOOLS])`
— a strict 18-tool allowlist. Two extension packages registered tools that the orchestrator's
constitution mandates but the runtime gate excluded:

1. `@cortexkit/aft-pi` registered 11 AFT tools: `aft_callgraph`, `aft_conflicts`, `aft_delete`, `aft_import`, `aft_inspect`, `aft_move`, `aft_outline`, `aft_refactor`, `aft_safety`, `aft_search`, `aft_zoom`.
2. `@cortexkit/pi-magic-context` registered 5 ctx tools (in addition to `todowrite` which GC-2026-081 already added): `ctx_search`, `ctx_memory`, `ctx_note`, `ctx_reduce`, `ctx_expand`.

The orchestrator's constitution repeatedly directs the LLM to use these tools:

- **AGENTS.md**: "Use `aft_search` (preferred over bash grep)" — code exploration directive.
- **AGENTS.md**: "Use `ctx_search` (provided by `magic-context`) before re-deriving project knowledge" — cross-session memory directive.
- **SYSTEM.md** (orchestrator constitution): AFT + ctx_* appear in the tool reference.
- **DEVELOPER_PROMPT** (built-in): tool-preference ladder "MUST call `aft_search` / `aft_outline` / `aft_zoom` before any bash `grep` / `rg` / `find` / `cat`"; "MUST reach for `ctx_search` before re-deriving project knowledge".

But all 16 of those tools were unreachable because the orchestrator's `setActiveTools` allowlist didn't include them. Empirically confirmed in round 2 of today's live test session: `aft_search` returned "Tool aft_search not found".

## Root cause

This is the **third consecutive GC** where the registration-vs-allowlist drift pattern surfaced. The pattern is mechanical:

1. An extension package (pi-magic-context, AFT) registers tools at pi's extension boot.
2. The orchestrator's `setActiveTools` allowlist does NOT include them.
3. The orchestrator's constitution (SYSTEM.md / AGENTS.md / DEVELOPER_PROMPT) advertises the tools.
4. The LLM has no schema to call the tools, but the constitution tells it to.
5. The drift is invisible until the LLM tries to call the tool.

GC-2026-081 fixed the same bug for `todowrite*` (3 tools). This GC extends the pattern to AFT (11) + ctx_* (5), bringing the total toolset from 18 → 34.

The drift accumulated gradually because:

1. Each extension added tools independently (pi-magic-context added `todowrite` then `ctx_*`; AFT added `aft_*`).
2. The orchestrator's allowlist was set once (15 tools, post GC-2026-073) and updated manually each time.
3. No verifier cross-checks the orchestrator's exported allowlist arrays against the set of tools registered by all loaded extensions.
4. The bug only manifests as missing tool schemas in the LLM's context — nothing crashes, nothing logs, the LLM just doesn't know the tools exist.

GC-2026-083 (proposed `verify:allowlist-sync` gate) would mechanically catch this drift class going forward.

```typescript
    "aft_move",

    "ctx_search",
    "ctx_memory",
    "ctx_note",
    "ctx_reduce",
    "ctx_expand",

```

Spread both into the `session_start` `setActiveTools` array at extension.ts:175-181:

```typescript
const tools: string[] = [
    ...ORCHESTRATOR_TOOLS,
    ...SUBAGENT_TOOLS,
    ...BASELINE_TOOLS,
    ...TODOWRITE_TOOLS,
    ...AFT_TOOLS,    // GC-2026-086
    ...CTX_TOOLS,    // GC-2026-086

pi.setActiveTools(tools);
```

The existing 18 tools remain in the active set; the two new constants add 16 more for a total of 34.

## Lessons

1. **Three consecutive GCs is a pattern, not a coincidence.** The registration-vs-allowlist drift class has now surfaced 3 times across GC-2026-081 (todowrite), GC-2026-085 (related return shape), and GC-2026-086 (aft + ctx). `verify:allowlist-sync` is overdue. Ship it as a blocker.

2. **The setActiveTools allowlist is a manual curatorial artifact.** It started at 15 (post GC-2026-073), grew to 18 with GC-2026-081 (todowrite), now 34 with GC-2026-086 (aft + ctx). Each growth required a manual edit + test. A verifier that asserts every registered tool is in the allowlist (or explicitly marked `disableActiveToolsFilter: true`) would prevent the next manual edit + the next drift.

3. **`ctx_*` was overlooked in GC-2026-081.** When GC-2026-081 added `todowrite` to the allowlist, it added `todowrite_compile` + `todowrite_progress` from the orchestrator's own package, but missed the 5 `ctx_*` tools registered by the same magic-context package. A mechanical verifier would have caught this.

4. **Constitution + runtime gate must be checked together.** Same lesson as GC-2026-081's postmortem #1, now reinforced across 3 GCs. The orchestrator's `verify:soft-mode-mental-model` gate already cross-checks SOFT_MODE_REMINDER against `src/extension.ts`; extending that pattern to all SYSTEM.md tool references is the natural next move.

5. **Live tests surface what unit tests can't.** Round 2 of today's live test session caught the missing aft_*/ctx_* tools because we tried to call them. Unit tests of the orchestrator's allowlist arrays passed — they didn't exercise the cross-extension registration mapping. A `verify:allowlist-sync` gate would close this gap.
