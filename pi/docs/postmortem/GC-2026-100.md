# GC-2026-100 — Postmortem

## What happened

One small dead-code cleanup closed. The original Batch C scope (R3 +
M12) collapsed to R3 only: M12 (personal_todowrite → agent_todowrite
rename) was already shipped by `GC-2026-path-B-field-renames`
(commit `231dc4f refactor(subagents): personal todowrite -> agent_todowrite (M12)`,
merged 2026-10-01 via `354e2b6`).

The remaining item — `RunContext.executeTool` and its `unwrapExecuteToolOutcome`
helper — was a path-A leftover. Path A (the in-process state machine)
used `ctx.executeTool` to drive pi-tasks's `TaskCreate` / `TaskUpdate`
directly. Path B (GC-2026-path-B-swap) replaced that round-trip with
the event-driven contract (`workflow:start` + `workflow:phase-complete`),
but the wiring on the planning side survived as dead surface.

## Root cause

`RunContext.executeTool?: (name: string, args: unknown) => Promise<unknown>`
was declared on `workflow-run.ts:291` (the RunContext interface) and
populated by `workflow-run-tool.ts:76-77` (a wrapper around
`ctx.executeTool` that unwrapped the `AgentToolCallOutcome` envelope
via `unwrapExecuteToolOutcome`). The `executeWorkflowRun` body never
read `runCtx.executeTool` — the wiring was a passthrough that fed into
nothing.

The unwrap helper itself (`unwrapExecuteToolOutcome`) was similarly
dead. It was exported, had its own 4-case test suite, and was referenced
only by `workflow-run-tool.ts:77` and the test file. Pure ceremony.

The dead surface persisted for ~14 days between path B landing
(2026-09-22) and this GC (2026-10-06), because:

- Path B's commit message focused on the workflow slim state machine,
  not on cleaning the planning-layer callers that became unreachable.
- The tests for `unwrapExecuteToolOutcome` passed at runtime — the
  function exists, has correct behavior, just isn't called from any
  production path.
- Typecheck did not catch it because `executeTool` is `?:` (optional)
  — both declaring it and not reading it are type-safe.

The entire test file was about `unwrapExecuteToolOutcome`. With the
helper gone, the tests pin a contract that no longer exists. Deleted
the file rather than commenting out the `it` blocks — they had no

## Behavior change (deliberate)

Zero runtime behavior change. The deleted code was unreachable from
any production path:

- `executeWorkflowRun` already completes the workflow without ever
  invoking `runCtx.executeTool`.
- The orchestrator session (where `workflow_run` is exposed) does not
  notice the absence — it just sees a slimmer `RunContext` shape.
- Test count drops by exactly 4 (the deleted helper's test cases).
  No other test asserts on `executeTool` or `unwrapExecuteToolOutcome`.

## Lessons

1. **Dead `?: optional` fields compile cleanly.** A field declared
   with `?:` is type-safe to declare AND to never read. The
   orchestrator's `RunContext.executeTool` survived 14 days post-path-B
   because nothing (typecheck, tests, runtime) flagged it. Sages has
   no rule against optional fields that go unused — they could
   surface in a future code review or a stricter linter, but for
   now they're silent. The fix is exactly this kind of GC.

2. **Helper + dedicated test file = ceremony that hides orphaning.**
   `unwrapExecuteToolOutcome` had 4 dedicated test cases that all
   passed at runtime. Their green-ness made the function look
   legitimately tested, not orphaned. The lesson: a green test suite
   proves "this function works" but not "this function is called".
   For reachability, a static call graph is the right primitive (and
   no Sages tool currently provides it).

3. **Header comments outlive the contracts they describe.** The
   original `workflow-run-tool.ts` header claimed the tool "needs
   access to ctx.executeTool so it can drive pi-tasks' TaskCreate /
   TaskUpdate from inside the workflow_run state machine." That was
   true under path A. After path B, the comment became a lie about an
   unreachable code path. Header comments should be updated when the
   code they describe changes shape — a small change, easy to skip.
