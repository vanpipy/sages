gc_id: GC-2026-094
title: Consume verdict-file fallback in audit gate
severity: minor
---

## What happened

The orchestrator's audit gate (the post-tool detector that checks
for stuck-on-same-call patterns) was updated to fall back to reading
the durable verdict file (`.pi/orchestrator/verdict-{task_id}.md`)
when the LLM's final message fence is missing or malformed. Pre-GC-094
the gate would silently bail when the fence was missing, which led
to false positives in the "stuck on Review" detector.

## Root cause

GC-2026-097 introduced the verdict file as a durable backup for
the Reviewer's final message. The audit gate was written before that
and didn't know about the fallback. This GC taught the gate to
prefer the durable file when the in-message fence is absent.

## Fix

Updated the audit gate's verdict-parsing logic to:
1. Try the in-message YAML fence first (the normal path).
2. If missing or malformed, read `.pi/orchestrator/verdict-{task_id}.md`
   and parse the file's YAML block instead.
3. If both fail, log a warning + return `null` (existing behavior).

## Follow-ups

- The durable verdict file is now the canonical fallback for the
  Reviewer. Workflow_run was the original consumer (it was the one
  that hit the "stuck on Review" detector); post-GC-2026-remove-workflow-run-prod
  the orchestrator's audit gate is the only consumer.
- See `pi/docs/postmortem/GC-2026-115.md` (FU3 follow-up) for the
  related fix to the workflow-handler's verdict-parser integration.
