# GC-2026-094 — Sub-agent max_turns boundary survival

## What happened

3 Developer dispatches and 1 Auditor dispatch all triggered `max_turns` abort at ~60 tool_uses — the default developer/auditor turn budget from `pi-subagents/src/budget.ts`. All substantive output was durable on disk:

- Developer: every RED/GREEN phase ended with a `git commit` (per `COMMIT_DISCIPLINE_SECTION` from GC-2026-038 T1). Commits survive the boundary.
- Auditor: `.pi/orchestrator/audit-{task_id}.md` was written during Step 6 of the audit procedure (before the final message). The orchestrator's `parseAuditReport` reads the verdict line + Concerns bullets from that file via regex — survives the boundary.

But the YAML verdict block at the END of the final assistant message was lost. The orchestrator's `extractStructuredOutput` parses that YAML block mechanically; on a boundary-aborted dispatch the parser returns `null` and the audit gate fires `missing_yaml_block`. Two real problems:

1. **Resilience gap** — The YAML block is the structured form of the dispatch's outcome. Losing it means the orchestrator has to fall back to a regex parse of the markdown audit file (for auditors) or skip the structured summary entirely (for developers). For developers there is no fallback path.
2. **Process violation signal** — The audit gate's `missing_yaml_block` finding is a content rule, not a process rule. It fires equally on a typo and on a boundary-aborted run; the orchestrator can't distinguish the two without inspecting the abort metadata.

## Root cause

The prompt-level discipline for max_turns survival was missing. The existing prompts (DEVELOPER_PROMPT, AUDITOR_PROMPT) carried:

- `COMMIT_DISCIPLINE_SECTION` (GC-2026-038 T1) — commits at every RED/GREEN phase. **Already durable.**
- `CHECKPOINT_PROTOCOL_SECTION` (GC-2026-038 T3) — `[checkpoint N/200 turns, Xm]` line every 5 turns so the orchestrator can detect stuck patterns. **Progress signal, not durability.**
- `FINAL_VERDICT_ADDENDUM` (GC-2026-037 T2) — final-message YAML block schema. **In-conversation, lost on boundary.**

What was missing:

1. **"Commit-then-cleanup" ordering rule** — agents doing refactors, lint cleanups, biome fixes, etc. AFTER the GREEN commit but BEFORE the final message were spending the remaining turns on cleanup that wasn't durable. The boundary flipped and only the cleanup was lost.
2. **Verdict-file durability backup** — the YAML block existed only in the final message. The agent had no prompt-level instruction to mirror it to a file the orchestrator could read independently.
3. **Directive soft-limit steer** — the existing steer message was generic ("Wrap up immediately — provide your final answer now."). It named NO concrete actions; the agent had to improvise under time pressure.
4. **File-level parser fallback** — `extractStructuredOutput` had no sibling that read the verdict file when the message YAML was missing.

The root cause is therefore a prompt-level gap: the discipline for surviving the boundary was implicit in the agent's good judgment, not encoded as MUST-level rules.

## Fix

Three coordinated changes pinning the boundary-survival discipline at the prompt, runtime, and audit-gate layers.

### 1. Prompt-level: `BOUNDARY_DISCIPLINE_SECTION` in DEVELOPER_PROMPT + AUDITOR_PROMPT

A new section in both prompts (lines 110-150 of `pi-subagents/src/agent-prompts/developer.ts`, lines 33-72 of `pi-subagents/src/agent-prompts/auditor.ts`) encoding four MUST rules:

- **Commit-then-cleanup ordering**: land the GREEN-test commit FIRST, secondary commits SECOND, YAML verdict LAST.
- **Durable verdict path**: `.pi/orchestrator/verdict-{task_id}.md` — explicit path, not just a "save your work somewhere" suggestion.
- **Soft-limit steer behavior**: when the orchestrator's nudge fires, do (1) commit pending work, (2) write the verdict file, (3) emit the in-message YAML. Do NOT start new work, tests, or refactors after the nudge.
- **Auditor-specific durability map**: notes that `audit-{task_id}.md` is already durable; the YAML file is the missing backup for the YAML block specifically.

Pinned by 8 new tests in `pi-subagents/test/developer-prompt.test.ts` (4 cases: section header, verdict path, ordering rule, position between Checkpoint Protocol and Final Verdict) and 9 in `pi-subagents/test/auditor-prompt.test.ts` (4 cases: section header, verdict path, audit-durable phrasing, position before Final Verdict).

### 2. Runtime-level: `SOFT_LIMIT_STEER_MESSAGE` directive + `extractStructuredOutputFromFile`

`pi-subagents/src/agent-runner.ts` lines 175-196 export a new `SOFT_LIMIT_STEER_MESSAGE` constant. Replaces the generic message at the soft-limit steer site (line 1161) with a directive that names the three concrete closing actions and explicitly forbids new work. Pinned by 3 tests in `pi-subagents/test/agent-runner-boundary-survival.test.ts` (references the durable verdict file path, tells the agent to commit before cleanup, forbids new work after the nudge).

`pi-subagents/src/agent-runner.ts` lines 1669-1686 export `extractStructuredOutputFromFile(taskId, cwd)` — sibling of `extractStructuredOutput(text)`. Reads `<cwd>/.pi/orchestrator/verdict-{task_id}.md` and runs `extractStructuredOutput` on the contents. Returns `null` on file-missing / malformed. Pinned by 5 tests (happy path, file-missing, directory-missing, malformed-file, round-trip with string helper).

### 3. Audit-gate level: `parseDeveloperYAMLWithFallback` + cwd threading

`pi-orchestrator/src/orchestrator-audit.ts`:
- Lines 829-855: new exported `parseDeveloperYAMLWithFallback(message, taskId, cwd?)` — message-first, file-fallback. Preserves backward compat when `cwd` is undefined.
- Lines 880-895: `parseAuditReportV2` extended with optional `cwd` parameter, routes through the new fallback wrapper.
- Lines 922-938: `aggregateTaskAudits` threads `cwd` through to every task.
- `initAudit` (line 334) and `completeAudit` (line 542) pass `cwd` to `aggregateTaskAudits` so both the init and complete paths honor the file fallback.

Plus `pi-orchestrator/src/orchestrator-audit.ts` lines 57-58 import the new `extractStructuredOutputFromFile` from `@sages/pi-subagents/agent-runner`.

Pinned by 7 tests in `pi-orchestrator/test/orchestrator-audit-verdict-file-fallback.test.ts` (T-FB-01..05 for the wrapper, T-V2FB-01..02 for `parseAuditReportV2` cwd threading).

### 4. Failure-mode catalog refresh

`pi-subagents/src/data/failure-modes.v1.yaml` — `subagent-timeout` description updated to acknowledge that partial-work durability now extends to `verdict-{task_id}.md` when the agent follows the Boundary Discipline prompt section. `pi-orchestrator/catalogs/gate.json` regenerated because `src/orchestrator-audit.ts` is in the catalog's source-files list.

## In-the-loop recovery

The boundary-survival pattern was demonstrated LIVE during GC-2026-094's own execution — 3 of 4 developer dispatches aborted at max_turns during REFACTOR or pre-commit phases:

| Task | Aborted at | Recovery | Commit landed |
|------|-----------:|----------|---------------|
| P1 (developer prompt) | tool_use #60 (after commit) | agent wrote report; orchestrator extracted `31e7eb0` | `31e7eb07d818b20c4581280bec8d5b0196a1e303` |
| P2 (auditor prompt) | tool_use #60 (REFACTOR — biome revert) | resumed agent with tight "commit-only, accept biome auto-fix" prompt | `de05400` |
| P3 retry (agent-runner) | tool_use #61 (after 8/8 GREEN + diff on disk, before commit) | orchestrator manually committed | `e513c91` |
| P4 (orchestrator-audit wiring) | tool_use #61 (after 7/7 GREEN, before broader suite) | orchestrator ran broader suite (848/848 pass), then committed | `01439f5` |
| P5 (verifier-driven audit) | tool_use #61 (after SC1-SC8 verified, before SC9 writes) | orchestrator writes audit-P5.md, postmortem, gc-index row from extracted verdict data | (no code commit) |

Each recovery preserved the durable artifact: the agent's substantive work landed on disk before the boundary, and the orchestrator closed the durable loop (commit / write postmortem / write gc-index) on the agent's behalf.

This validates the GC's premise at a meta-level: when the agent boundary flips, the durable artifacts (commits + file writes) survive. Only the in-conversation summary is lost — and the new `extractStructuredOutputFromFile` makes even that loss recoverable for the structured-output path.

## Follow-ups

### F1: future agent prompts should commit-first (high)

The 3 aborts all happened while agents were doing post-commit work (REFACTOR, broader suite, postmortem writes). The fix is to put the smallest commit FIRST in the prompt's task ordering, then build up. Concretely:

- For prompts that combine multiple changes, sequence them as separate `git commit` calls with the smallest first.
- For prompts that end with a broader test suite, run the targeted tests FIRST, commit, then run the broader suite.
- For verifier-driven audit prompts, write the audit report BEFORE the postmortem (so the postmortem can cite the audit's verdict, and the audit survives if the postmortem aborts).

### F2: extend Boundary Discipline to merger (deferred)

`pi-subagents/src/agent-prompts/merger.ts` lacks a Boundary Discipline section analogous to the new sections in developer.ts / auditor.ts. Today merger's runtime is short enough that the discipline isn't needed, but if cross-workspace merges grow past 60 tool_uses the same failure mode will appear. Revisit if/when merger runtime grows.

### F3: cookbook candidate — soft mode + agent boundary survival

Reusable recipe for any LLM-orchestrated workflow that hits turn budgets. Outline:

- **Order work by durability** — smallest commit first, build up.
- **Mirror structured output to disk** — every final-message YAML block has a `<cwd>/.pi/orchestrator/{name}-{id}.md` mirror.
- **Directive soft-limit nudges** — name the concrete closing actions, forbid new work.
- **File-fallback parser** — every structured-output parser has a sibling that reads the disk mirror when the in-message form is missing.
- **Orchestrator recovery** — when the agent boundary flips, the orchestrator commits on the agent's behalf using the durable on-disk state.

Worth promoting to `pi/docs/cookbook/` once a second GC validates the pattern across a different failure surface.
