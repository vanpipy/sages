# GC-2026-058 — Verdict enforcement (machine-enforced REVISE/REJECT gate)

> **Date:** 2026-08-20
> **Status:** Resolved
> **Severity:** major

## What happened

`orchestrator_audit` could return a REVISE or REJECT verdict, and
the LLM could ignore it and proceed with the next `task_dispatch`.
The audit was informational, not enforced — there was no machine
contract that forced the LLM to acknowledge failure.

In a 4-stage DAG workflow, this means a failed audit doesn't
actually stop the workflow. The LLM can decide to push forward
anyway, run the next batch, and re-audit. By the time the next
audit runs, the workflow has already executed the next batch
under potentially-failing conditions.

## Root cause

`orchestrator_audit` (in `pi/src/tools/orchestrator/orchestrator-audit.ts`)
returns a verdict in the `complete` observation. The result is
written to the audit state file. But the dispatch state machine
(in `task-dispatcher.ts`) has no awareness of the latest audit
verdict — it just dispatches the next task.

The LLM had full agency to acknowledge the verdict (or not) and
proceed. This is the same pattern as the goal-modification issue
(GC-2026-057): the LLM has the structural ability to bypass
checks.

## Fix

New module `pi/src/tools/orchestrator/verdict-enforcement.ts`:

### 1. Sidecar state file

`verdict-state-{dag_id}.yaml` — separate from `audit-state-*.yaml`
so audit lifecycle and gate state stay decoupled. The verdict
state records:

- `verdict`: PASS / REVISE / REJECT
- `score`: 0-100
- `audit_at`: ISO 8601 timestamp
- `acknowledged`: bool
- `acknowledged_at` + `acknowledged_reason`: when acknowledged

The audit-state lifecycle (init / recording / complete) and the
verdict-gate contract (open / closed / acknowledged) are
intentionally separate concerns. The gate is a "current state"
flag; the audit-state is a record of what happened.

### 2. Three functions

`recordVerdict(cwd, dagId, verdict, score)` — called by
`orchestrator_audit` on `complete` observation. PASS is
auto-acknowledged (the gate is open). REVISE/REJECT start
unacknowledged.

`acknowledgeVerdict(cwd, dagId, reason)` — flips the acknowledged
flag. Idempotent (a second ack doesn't overwrite the first
reason). Returns the updated record.

`checkVerdictGate(cwd, dagId): VerdictGateResult` — returns
`{open, record, reason, errorMessage}`. The `errorMessage` is
LLM-actionable: it tells the LLM to either re-run the audit or
pass `acknowledge_verdict: { reason: '...' }` to `task_dispatch`.

### 3. Integration note

The gate is implemented as a pure helper. Wiring it into
`task_dispatch` is left as a follow-up (would require touching
the dispatch state machine). The helper is the building block;
the gate can also be invoked from custom orchestrator code.

The decoupling is intentional: the gate's invariants are easier
to reason about when the gate is a separate function, not a
state-machine hook.
