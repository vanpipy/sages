# GC-2026-093 — Subagent rename: Plan → PlanCompiler

## What happened

The `Plan` subagent's name read as "the agent that plans" — but Plan is actually a **plan compiler** that takes an already-decided Planning Brief from the main agent and renders it into an ordered implementation plan (or returns `PLAN_STATUS: BLOCKED`). The orchestrator IS the planner: it explores, decides architecture, weighs trade-offs, picks the approach, writes the goal contract, calls `dag_synthesize`. The Plan subagent never does that work; the per-agent `pi-subagents/src/agent-prompts/plan.ts` prompt explicitly forbids it.

The name confusion caused three real problems:

1. **Conceptual** — Users (and LLM-facing roster readers) thought Plan was the planner when the orchestrator is. Documenting this in the prompt wasn't enough; the name itself implied otherwise.
2. **Tooling surface** — The `Agent` tool's `subagent_type` parameter takes the name as-is. Future code (and the LLM-facing roster in `agent-tool-description.md`) is clearer with a name that matches the role.
3. **GC-2026-091 parity** — This rename mirrors the same registry layer touched by GC-2026-091 (PascalCase canonicalization + git-expert removal). The case-insensitive `resolveKey()` machinery already in place makes the rename backward-compatible: old DAG YAMLs using `subagent_type: "Plan"` continue to work; new code SHOULD use `PlanCompiler`.

## Root cause

Initial naming in DAG-2026-017 was "Plan" because the brief→plan rendering was conceptually a planning task, even though the prompt strictly forbids the agent from doing actual planning. The naming escaped review because:

- The prompt content (which forbids planning) was the load-bearing constraint, not the name
- No test pinned the registry's canonical name as the user-facing description
- The LLM-facing roster just listed the name without commentary

GC-2026-091 touched this same registry layer (PascalCase + git-expert removal) but did NOT consider the rename — the dispatch surface at that time was small and the legacy name felt familiar.

## Fix

A dual-key Map entry. The `DEFAULT_AGENTS` Map in `pi-subagents/src/default-agents.ts` now has BOTH keys pointing to the same `PLAN_AGENT` constant:

```ts
const PLAN_AGENT: AgentConfig = {
    name: "PlanCompiler",      // canonical name (formerly "Plan")
    displayName: "PlanCompiler",
    description: "Plan compiler — converts a main-agent Planning Brief…",
    builtinToolNames: ["read"], // unchanged
    extensions: false,          // unchanged
    excludeExtensions: ["pi-subagents"],
    skills: false,
    model: "anthropic/claude-haiku-4-5", // (correctly P2-uncovered; see risk below)
    thinking: "minimal",        // unchanged
    systemPrompt: PLAN_PROMPT,  // prompt file still plan.ts
    promptMode: "replace",
    isDefault: true,
    maxTurns: 12,               // unchanged
    runInBackground: false,     // unchanged
    inheritContext: false,      // unchanged
    maxConcurrent: 2,           // unchanged
};

export const DEFAULT_AGENTS: Map<string, AgentConfig> = new Map([
    // ...
    ["PlanCompiler", PLAN_AGENT],  // canonical (primary)
    ["Plan",        PLAN_AGENT],  // legacy alias for backward compat
    // ...
]);
```

## Risks + watchpoints

- **Internal documentation vs user-facing descriptions** — The `subagents.json` `_comment` field still mentions `Plan remains a legacy alias in the registry (existing DAG YAMLs reference subagent_type: "Plan")` because that's internal documentation explaining backward compat. The LLM-facing descriptions (agent-tool-description.md, orchestrator SKILL.md roster) were cleaned to remove `(alias ...)` parentheticals. This is the right separation: maintainers need to know about the alias; users reading the agent description don't.

- **"Why not Planner"** — `Planner` would re-introduce the exact confusion this GC is fixing. The Plan subagent does NOT plan; it compiles a brief into an ordered list. Adding `Planner` as an alias would imply that calling it triggers planning, when in fact the orchestrator does the planning. **Anti-goal: do NOT add `Planner` as a future alias.**

- **The hardcoded `model: "anthropic/claude-haiku-4-5"` in `PLAN_AGENT`** — GC-2026-092's resolution chain (per-type override → `AgentConfig.model` → `settings.json#defaultProvider/defaultModel`) silently falls through when the model string can't be resolved (latent bug in `tryProviderModel` — see GC-2026-092's "What worked" / "Risks"). Today, the per-type `defaultModelsByType: { PlanCompiler: "minimax/MiniMax-M2.7-highspeed" }` from the subagents.json template wins, so PlanCompiler uses the M2.7-highspeed model in fresh installs. The hardcoded `claude-haiku-4-5` is only used if someone clears their template defaults AND has `claude-haiku-4-5` in their registry. The deeper fix (resolving bare names in `tryProviderModel`) is a follow-up GC.

- **Existing DAG YAMLs continue to work** — Any DAG using `subagent_type: "Plan"` resolves through the dual-key Map entry to the same `PLAN_AGENT`. No migration needed for existing DAGs.

- **LLM-facing roster tests** — `agent-frontmatter-verify.test.ts` previously used regex `name:\s*"Plan"` to extract the Plan block from `default-agents.ts`. After the rename, the literal `name: "Plan"` doesn't exist in the source. The test was updated to use `"PlanCompiler"`. A more robust approach would be to enumerate the Map keys directly (not regex-match the source). This is a T2 follow-up.

## Follow-ups

1. **T1 (suggested)** — A future strict-mode `Planner` agent could ship that BLOCKs on missing decisions (vs the current PlanCompiler which BLOCKs on missing Brief content). Today the orchestrator handles this role; an explicit Planner agent would be redundant for the Sages 4-stage DAG workflow. Future users who write plain-`pi` workflows (not using Sages orchestrator) might benefit from such an agent. Out of scope for this GC.

2. **T2 (suggested)** — The LLM-facing roster tests (`agent-frontmatter-verify.test.ts`) rely on regex extraction of source files. A more robust approach is to import `DEFAULT_AGENTS` directly and assert on its Map keys. Tied to the broader verify:gcdb content-blind check (from GC-2026-091's T2 and GC-2026-092's T2). Future GC: ship `verify:subagent-roster` that cross-checks the agent-tool-description.md roster against the registry keys.

3. **T3 (suggested)** — Rename the source file `pi-subagents/src/agent-prompts/plan.ts` to `plan-compiler.ts` for symmetry with the agent's canonical name. Low priority — the file name doesn't have to match the agent name; the prompt content is what matters. Would require updating imports in `default-agents.ts`.

4. **T4 (deferred)** — The `tryProviderModel` resolver bug (no-slash bare names silently fall through to parentModel) still exists. Today it doesn't cause issues because the per-type `defaultModelsByType` from the template uses `provider/model` format. But if a user writes `Agent({ model: "MiniMax-M3" })` (no slash), it would silently fall through. Defer to a future GC focused on the resolver.

## What worked

- **User-driven naming review** — The user noticed the conceptual confusion (Plan = plan-maker vs orchestrator does planning). Their follow-up ("the user wants to make the thing right") set the bar for a full rename rather than just documentation. Result: a clean canonical name that matches the role.

- **User-driven cleanup** — The user also caught the `(alias ...)` parenthetical noise in the LLM-facing descriptions. Without that follow-up, the description would have advertised both names side-by-side, defeating the point of the rename.

- **Dual-key Map entry as backward-compat strategy** — Old DAG YAMLs reference `subagent_type: "Plan"`. By adding both keys to the Map (rather than renaming + redirecting), the rename is fully backward-compatible at zero migration cost. The case-insensitive `resolveKey()` machinery from GC-2026-091 makes this even more forgiving.

- **Managed-worktree isolation + per-batch TDD** — Each phase (P1: registry, P2: type unions, P3: roster+template, P4: postmortem) landed in its own commit with RED-then-GREEN discipline. The merge diff is 13 files because each commit was self-contained, but the per-phase commits preserved a clean history on the integration branch.

- **Cleanup of legacy deadline branch** — The `resolveDeadlineMs()` if-check in settings.ts was inconsistent (had `Plan` and `PlanCompiler` as separate branches even though both go through `resolveRunConfig` after GC-2026-091). User caught this during review; cleanup removed the redundant branch.
