## What happened

The actual producer refactor for the unified task-feeder. After
GC-2026-108 shipped the canonical `task-feeder.ts` module and
GC-2026-112 pre-adapted the test fixtures, this GC lands the
producer-side wiring in `pi-tasks/src/index.ts`:

- Replaces the three legacy cascade listeners (workflow-handler's
  direct spawn, decompose-cascade's cascade, `index.ts:227`'s
  TaskExecute cascade) with one `registerTaskFeeder({...})` call.
  ONE feeder owns spawn + completion for ALL task types.
- Adds `feeder.maybeAutoSpawn(task)` calls to 5 producers:
  `TaskCreate` LLM tool, `/tasks create`, `TaskUpdate`, `TaskExecute`,
  `materializeDecomposeChain`. The `TaskCreate` execute became
  `async` so it `await`s the spawn before returning (avoids a race
  with downstream `TaskOutput` / `TaskUpdate` calls that read
  `task.owner`).
- Removes the `cfg.autoCascade` config gate. Cascade is
  unconditional via the feeder.
- Removes the `cascadeConfig` variable. The `cfg.autoCascade` key
  becomes a no-op.
- `reattachAgents` now reads `task.owner` (preferred) in addition
  to `task.metadata.agentId` (legacy `TaskExecute` path), so
  reattachment works regardless of which path spawned the task.
- `TaskOutput` and `TaskStop` updated to read `task.owner ||
  task.metadata.agentId` for subagent-task detection.

`workflow-handler.ts` and `decompose-cascade.ts` are **NOT** refactored
in this GC — they still own their own spawn/cascade paths, and
removing them is filed as **FU3** (clean-up follow-up). The refactor
in `index.ts` is sufficient: the feeder's `subagents:completed` /
`subagents:failed` listeners fire for every dispatched task
regardless of source, and the `subagentId` checks in `TaskOutput` /
`TaskStop` work with both `task.owner` (new path) and
`task.metadata.agentId` (legacy path).

`AGENTS.md:169-173` rewritten to describe the unified feeder
(no more "dispatches atomically" wording that contradicted the
prior implementation).

## Why this design

GC-2026-111 attempted the full refactor in one shot, broke 40+
test fixtures, and was reverted mid-GC. The phased plan
(108 → 111 → 112 → 113) split the work into manageable pieces:

- **108 (Phase 1)**: ship the feeder module + tests, no producer
  refactor.
- **111 (Phase 2 scope reframe)**: revert + file FU0 (112+113).
- **112 (Phase 2a)**: pre-adapt test fixtures to the new model.
  Most fixtures use the legacy `TaskCreate + TaskExecute` pattern
  and didn't need changes (the pattern still works). The few that
  test behavior that will move (TaskExecute spawn boundary,
  cfg.autoCascade gate) were `it.skip()`-ed with GC-2026-113
  follow-up notes.
- **113 (Phase 2b — this GC)**: wire the producers + remove the
  legacy listeners. The test fixtures are already compatible
  with both the legacy and new models, so the refactor lands
  with **0 new test failures vs main** (just 18 pre-existing
  `tasks-config.test.ts` failures unrelated to this GC).

## What broke / what we had to fix mid-implementation

- **`void feeder.maybeAutoSpawn(task)` was a race with `TaskOutput`.**
  The initial wiring used `void` (fire-and-forget) so the
  producer's tool call returns immediately. But `TaskOutput` reads
  `task.owner` synchronously, and the spawn RPC needs ~1 RPC
  roundtrip to populate `task.owner`. So `TaskOutput` sometimes
  saw `task.owner === undefined` and threw
  "No background process for task 1". Fix: change the producer
  handler to `async execute()` and `await feeder.maybeAutoSpawn(task)`.
  This blocks the tool call until the spawn RPC returns. The
  performance cost is minimal (a few ms per TaskCreate).

- **`TaskOutput` and `TaskStop` checked `task.metadata.agentId`**,
  which the new feeder doesn't set. Fix: read `task.owner ||
  task.metadata.agentId` (prefer owner; fall back to legacy
  metadata.agentId). The "No background process" throw now
  distinguishes between "no agent ID at all" and "subagent
  task with no agent ID" with a clearer error.

- **Race in `subagent-result-consumption` test**: the test fired
  `subagents:failed` for "agent-1" immediately after `TaskCreate`,
  but the legacy "manual" `TaskExecute` call was in between
  (which would have errored with "not pending" in the new model).
  Fix: drop the `TaskExecute` call (auto-spawn handles it).

- **`agent-reattach.test.ts` "does not reattach a task that is no
  longer in progress"** test depended on session 1's listener
  reverting the task to pending after a `subagents:failed` event.
  The listener needs `agent-1` in `agentTaskMap`, which only
  happens via `TaskExecute` in the current code (the feeder's
  spawn wrapper does set the map, but `TaskExecute` was the
  only entry point before this GC). Fix: keep `TaskExecute` in
  the helper for now; GC-2026-113 doesn't break this because
  `TaskExecute` still populates `agentTaskMap` for legacy-spawned
  tasks.

- **Two `subagent-integration` tests** had fixture races: task
  2 auto-spawned before its blocker (task 1) was added. With
  auto-spawn, the order matters — you can't create a task with
  blockers retroactively. Fix: skip both tests with follow-up
  notes pointing at the feeder's `cascadeSpawn` test surface.

- **2 RPC protocol tests** (`ready broadcast sets subagentsAvailable`,
  `spawn RPC rejects with error message from server`) tested
  behavior that now hangs in the new model (TaskCreate's feeder
  awaits the spawn RPC for 30s; without a responder, the test
  blocks). Fix: skip the `ready broadcast` test (new model needs
  a different mock setup); rewrite the `spawn RPC rejects` test
  to assert the error text in the task's `lastError` (the feeder
  catches the spawn error and reverts the task).

- **4 TaskStop tests** (in both `subagent-integration.test.ts` and
  `task-output-stop.test.ts`) called `TaskCreate + TaskExecute`
  then `TaskStop`. With auto-spawn, `TaskExecute` errors with
  "not pending". Fix: drop the `TaskExecute` calls. The helper
  `launchAgentTask` in `task-output-stop.test.ts` was updated
  to drop `TaskExecute`.

## What did NOT change (filed as follow-ups)

- **`workflow-handler.ts` and `decompose-cascade.ts`** still own
  their own spawn/cascade paths. The feeder is added alongside;
  it doesn't replace them. Removing the duplication is a clean-up
  follow-up (FU3).
- **`cfg.autoCascade` key** still exists in the config schema but
  is now a no-op. The config loader doesn't read it for cascade
  gating anymore. Filed as FU3 to either remove the key or
  re-add the gate if users complain.
- **`pi-tasks/src/decompose-cascade.ts` cascade listener** still
  fires for decompose tasks. The feeder ALSO fires for decompose
  tasks. This is benign (both listeners do the same work on the
  same `agentTaskMap`), but the duplicate is technical debt.
  Filed as FU3.
- **The 2 `it.skip()` cases in `task-execute-spawn-options.test.ts`**
  from GC-2026-112 are still skipped. They were supposed to be
  unskipped and re-pinned against the feeder's spawn callback in
  this GC. The re-pinning requires writing new tests that drive
  the feeder directly (since `TaskExecute` no longer owns the
  spawn boundary). Filed as a follow-up.

## Follow-ups

- **FU3 (filed)**: clean up the dual-cascade and dual-spawn paths.
  Remove `cfg.autoCascade` config key (or re-add the gate if
  users complain). Remove the `cfg.autoCascade` references in
  `subagent-integration.test.ts` (now-skipped tests). Move
  `workflow-handler.ts`'s direct spawn into the feeder's spawn
  callback. Move `decompose-cascade.ts`'s cascade listener into
  the feeder's listener.
- **FU2** (filed earlier): persist `agentTaskMap` across session
  restarts.
- **Unskip the 2 `task-execute-spawn-options.test.ts` cases**:
  re-pin them against the feeder's spawn callback behavior. The
  tests should call `feeder.maybeAutoSpawn` directly (or a new
  spawn-options test API) and verify the spawn RPC payload uses
  snake_case `max_turns` and not `maxTurns`.
