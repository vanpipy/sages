# GC-2026-091 — Program-level plan → DAG → todo chain

## What happened

The orchestrator's chain `goal_contract_create → dag_synthesize → task_dispatch → todowrite item` had three structural defects that made the links LLM-remembered instead of program-level reliable:

1. **`todowrite_compile` was optional** — the LLM had to remember to call it after `dag_synthesize`; without the call the todo file had no `dag_id` at all (and no `goal_id` either).
2. **`GoalContract` had no `dag_id` field** — the goal ↔ DAG link was a hand-typed guess in `goal-{id}.yaml`. Reverse lookup (DAG → goal) was an O(N) scan over `.pi/orchestrator/goal-*.yaml`.
3. **`TodoFile` had no `goal_id` field** — the todo view could only trace back to its DAG, not its goal. End-to-end trace required two hops (todo → DAG → goal) instead of one.

The mechanism for completing a Goal Contract was therefore: synthesize DAG, then **remember** to compile todowrite, then **remember** to thread `dag_id` back into the goal yaml, then **remember** to populate `goal_id` on the todo. Three opportunities for the LLM to drop a step.

## Root cause

The schema additions were deferred when the orchestrator tools first shipped (GC-2026-060 added auto-todowrite, but it stayed LLM-triggered rather than orchestrator-internal). A prior attempt at this fix (GC-2026-068, commit `e7fc890`) tried to reach into magic-context's internal `setTodoSnapshot` API to drive the todowrite from outside — that API is not in MC's public exports, and the postmortem was reverted in `354b400`.

The lesson (carried into this GC's anti-goals): **don't touch MC internals** — drive the todowrite from inside the orchestrator's own `dag_synthesize`, where the goal-↔DAG edge is already known.

## Fix

Three optional fields added to internal types, plus one auto-sync step inside `dag_synthesize`. All public tool signatures (`goal_contract_create`, `dag_synthesize`, `todowrite_compile`, `todowrite_progress`) are unchanged — the chain is tightened by making the orchestrator do the threading itself.

| Phase | Change | Files |
|---|---|---|
| A | Add optional `dag_id` to `GoalContract`; `goal_id` to `TodoFile` | `pi-orchestrator/src/types.ts` |
| B | Validators accept optional fields; legacy yamls still load | existing validators in `state-persistence.ts` |
| C | `goalContractToYaml` emits `dag_id` line after `done_definition`; `dag_id` joins `HASHED_FIELDS` so adding it invalidates prior hash | `goal-contract.ts`, `goal-lock.ts` |
| D1 | `dag_synthesize` auto-calls `executeTodowriteCompile({ dag_id, force: true })` after persisting the DAG; surfaces error if `!ok` | `dag-synthesizer.ts` |
| D2 | `dag_synthesize` writes `plan.id` back into `goal-{goal_id}.yaml` as `dag_id`; recomputes `_lock_hash` if one was set | `dag-synthesizer.ts` |
| E | `executeTodowriteCompile` populates `file.goal_id = plan.goal_id` before saving | `todowrite.ts` |
| + | `canonicalize` skips undefined values recursively (was top-level only) so the lock hash is stable across YAML round-trips | `goal-lock.ts` |

The order inside `dag_synthesize` is **load-bearing**: D1 (todo compile) must run BEFORE D2 (goal writeback), because the todo file's `goal_id` is populated during compile from `plan.goal_id` — if D2 ran first, the goal writeback would have happened against a todo file that was still missing `goal_id`. The D1+D2 order test pins this invariant.

The D1/D2 error paths return `status: "error"` to the caller rather than silently succeeding with a half-synced chain. This is intentional — the original bug was that the chain COULD silently desync; the new behavior forces the caller to retry or accept the error.

## Risks + watchpoints

- **`canonicalize` behavior change** — recursive undefined-filter expands an existing top-level filter to nested fields. Backward-compatible (every existing test still passes), but any caller that stored the old (undefined-inflated) hash on disk will see a mismatch on first lock-check. There are no such callers today (`computeGoalHash`'s consumers all write-then-read the same form). Watch for this if a future GC introduces a separate hash-cache.
- **D1/D2 error path returns `status: "error"`** — previously silent success. Any orchestrator caller that relied on `dag_synthesize` always returning `status: "in_progress"` will now see an error wrapper when the auto-sync fails. This is intentional — silent fallbacks were the original bug. Callers that dispatch via `task_dispatch` will get the error through the standard error block; the orchestrator's `task-dispatcher.ts` does not need an update because the error wraps the synthesis response, not the dispatch.
- **`goalContractToYaml` line ordering** — `dag_id` is emitted immediately after `done_definition` to mirror the interface ordering in `GoalContract`. If the interface changes (new field inserted before `dag_id`), the serializer must be kept in sync manually — there's no schema-driven codegen for YAML serialization yet.

## Follow-ups

1. **T2 (suggested)** — extend the same auto-sync to `goal_contract_create` so DAG-less goals still get a writeback to their goal yaml (currently they don't — only `dag_synthesize` triggers the chain). Low priority because DAG-less goals are rare in practice.
2. **T3 (suggested)** — `audit-state-{dag_id}.yaml` fingerprint could include `goal_id` so dispatch can validate the chain programmatically before launching workers. Defense in depth.
3. **`wrapRegisteredTool` migration for `dag_synthesize`** — the wrapping logic in `executeDAGSynthesize` is hand-rolled (it's a large tool that does several things before returning). The GC-2026-090 helper would simplify the return shape, but the multi-step orchestration (emit D1 event → writeback D2 → emit success) doesn't fit the helper's single-execute shape cleanly. Track as separate refactor if a second orchestrator tool grows similar multi-step logic.

## What worked

- **Pre-research via git log + postmortem review** caught the GC-2026-068 MC-API mistake before the implementer could repeat it. The anti-goals section in `goal-GC-2026-091.yaml` cited the prior postmortem explicitly.
- **Strict TDD with RED→GREEN pairs in the same commit** — every schema addition shipped with its test in the same atomic commit. The merge diff is 13 files because each commit was self-contained.
- **Managed-worktree isolation** kept the orchestrator cwd clean during implementation. The branch was merged with `--no-ff` and the worktree is ready to destroy.
- **7-gate verification** caught the `verify:gcdb` regression at the right moment (post-merge, pre-cleanup) — without the postmortem write-back, the merge would have left the repo in a state where the gate fails on every CI run.
