## What happened

A post-GC-2026-115 audit of the task-feeding pipeline (`./pi-orchestrator/` × `./pi-tasks/`) flagged four minor findings (F3-F6) that were deliberately deferred to keep GC-2026-117 (the dead-code cleanup) focused. This GC addresses all four.

### F3 (P2) — no verifier for `workflow_run_goal_id` invariant

The task-feeder's `cascadeSpawn` (task-feeder.ts:146) skips tasks with `metadata.workflow_run_goal_id` set. If a workflow spec builder forgets to stamp this field, the workflow task would be picked up by the feeder's cascade instead of workflow-handler's — the prior-Review summary injection would never run, and the cascade would stall on the first phase. The mitigation was a comment at task-feeder.ts:138-145 explaining the partition; no automated guard existed.

### F4 (P2) — cross-package event channels duplicated as string literals

Three cross-package event channels had no single source of truth:

- `workflow:start` — emit: `pi-orchestrator/workflow-run.ts`; listen: `pi-tasks/workflow-handler.ts`
- `workflow:phase-complete` — emit: `workflow-handler.ts`; listen: `workflow-run.ts`
- `tasks:rpc:decompose-materialize` — emit: `pi-orchestrator/decompose-task.ts`; listen: `pi-tasks/index.ts`

String-literal duplication has historically led to drift (cf. `decompose:spawn` — emitted in one GC, never listened, removed in the next).

### F5 (P3) — `cascadeSpawn` walks full task store on every completion

```ts
async function cascadeSpawn(): Promise<void> {
  const all = store.list();
  for (const t of all) {
    if (t.status !== 'pending') continue;
    if (!isFeedableTask(t)) continue;
    if (typeof t.metadata?.workflow_run_goal_id === 'string') continue;
    await maybeAutoSpawn(t);
  }
}
```

O(N) per cascade, where N = total task count. Most pending tasks aren't children of the just-completed task — the iteration does redundant blocker checks for tasks that can't possibly be unblocked.

### F6 (P3) — redundant `completedIds: Set<string>` cache in workflow-handler

The cascade loop's blocker-completion query was:

```ts
if (!t.blockedBy.every(id => completedIds.has(id))) continue;
```

where `completedIds` was a Set populated in the `subagents:completed` listener. The Set's only purpose was to avoid `store.get()` calls inside the cascade loop, but `store.get()` is O(1) (Map lookup) and the cache's bookkeeping didn't justify the marginal speedup.

## Fix

### F6 — Remove completedIds cache

Deleted `const completedIds = new Set<string>()` and its 3 use sites. The cascade loop now reads `store.get(id)?.status === "completed"` directly. Behavior unchanged. Workflow-handler local state shrinks to the bookkeeping that's genuinely workflow-specific (activeWorkflowId, activeGoalId, maxFixIterations, maxRedesigns, fixIterationsUsed, redesignsUsed, findingsHistory, activeGoal).

### F5 — Pass completedTaskId to cascadeSpawn

```ts
async function cascadeSpawn(completedTaskId: string): Promise<void> {
  for (const t of store.list()) {
    ...
    if (!t.blockedBy.includes(completedTaskId)) continue;  // fast pre-filter
    await maybeAutoSpawn(t);  // still has blocker-every guard for multi-parent
  }
}
```

Both call sites (`subagents:completed` + `subagents:failed` "stopped" branch) updated. Top-level tasks (no blockers) are spawned directly by TaskCreate / TaskUpdate / materializeDecomposeChain through `feeder.maybeAutoSpawn`, so the cascade path doesn't need to consider them.

### F4 — Centralize event channels

New `pi-tasks/src/event-channels.ts`:

```ts
export const WORKFLOW_START = 'workflow:start';
export const WORKFLOW_PHASE_COMPLETE = 'workflow:phase-complete';
export const TASKS_RPC_DECOMPOSE_MATERIALIZE = 'tasks:rpc:decompose-materialize';
```

Consumers updated:
- `pi-orchestrator/src/workflow-run.ts` — import via `@sages/pi-tasks/event-channels` (TS path alias already configured in `pi-orchestrator/tsconfig.json`)
- `pi-orchestrator/src/decompose-task.ts` — same import path
- `pi-tasks/src/workflow-handler.ts` — relative `./event-channels.js`
- `pi-tasks/src/index.ts` — same

Out of scope (intentionally):
- `subagents:completed` / `subagents:failed` — owned by pi-subagents runtime; centralizing in pi-tasks would invert ownership.
- `subagents:rpc:*` — between pi-subagents and its callers (not cross-package between orchestrator + tasks).

### F3 — Add `verify:workflow-meta-invariant` gate

New `pi-orchestrator/scripts/verify-workflow-meta-invariant.ts`:

1. jiti-imports `pi-tasks/src/workflow-graph.ts`
2. Calls each spec builder (`buildStaticWorkflowGraph`, `buildFixTaskSpec`, `buildRedesignImplementTaskSpec`) with a minimal fixture
3. Asserts every returned spec carries `metadata.workflow_run_goal_id` set to the expected goal id

Why runtime (vs static regex): the spec builders compose their metadata via spread (`{ ...meta, phase: '...' }`) or via destructured args (`workflow_run_goal_id` as a function parameter). A regex check that looks for "workflow_run_goal_id appears in function body" would pass even if the field is silently dropped on the way to metadata. The runtime check verifies the actual returned shape.

Wired into `verify:all`. New gate output: `[workflow-meta-invariant] workflow spec builders stamp workflow_run_goal_id (GC-2026-118 F3)`.

Sanity-checked by temporarily sed-replacing `workflow_run_goal_id` → `XWORKFLOW_RUN_GOAL_ID` in workflow-graph.ts — the verifier exits non-zero with a ReferenceError pointing at the offending builder.

## Follow-ups

- **Event channel centralization for subagents-owned channels** — if pi-subagents ever needs to rename a subagents:* channel, the centralization is half-done. Could be addressed by adding a small `pi-subagents/src/event-channels.ts` exporting the subagents:* constants, then having pi-tasks import from there. Defer until there's a concrete motivation (a subagents:* channel rename).
- **True O(children) cascade via reverse index** — F5's `blockedBy.includes(completedTaskId)` is still O(N) to find the children. A `Map<parentId, Set<childId>>` reverse index maintained at store.create / store.update would give true O(children) cascade. Requires hooking into the TaskStore layer; invasive. Defer until N grows past ~500 tasks.
- **`workflow:phase-complete` payload schema versioning** — the event is emitted by workflow-handler.ts and consumed by workflow-run.ts, but the payload shape is implicit (the comment in workflow-run.ts describes the fields). F4 centralizes the channel name but the payload schema is still inline. A follow-up GC could define `WorkflowPhaseCompleteEvent` as an explicit type in `event-channels.ts` (or a new `event-schemas.ts`).
