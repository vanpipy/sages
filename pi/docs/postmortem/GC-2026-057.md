# GC-2026-057 — Goal lock (anti-cheat SHA-256 hash)

> **Date:** 2026-08-20
> **Status:** Resolved
> **Severity:** major

## What happened

The orchestrator could silently modify a goal.yaml to make its
own success criteria easier (drop hard SCs, replace strict
`verification_cmd` with `echo yes`). The audit phase would then
run the relaxed command and report PASS, despite the original
intent.

This is a structural anti-cheat gap: the goal contract is
write-once from the user's perspective, but the LLM has full
disk access. If the LLM decides mid-workflow that a goal is too
hard, it can quietly edit the file to make the SCs trivial.

## Root cause

`goalContractToYaml` (the serializer in
`pi/src/tools/orchestrator/goal-contract.ts`) writes the contract
fields but provides no integrity check on subsequent reads.
`loadGoalContract` returns whatever is in the file. If the LLM
modifies the file between creation and audit, the audit sees
the modified version and reports accordingly.

The 4-stage DAG workflow (goal → DAG → dispatch → audit) assumes
the goal is immutable. The assumption is correct from the user's
perspective (the user types the goal once), but the orchestrator
itself can edit its own goal at any time.

## Fix

New module `pi/src/tools/orchestrator/goal-lock.ts`:

### 1. Hash computation

`computeGoalHash(goal): string` — SHA-256 over the canonical JSON
form of the goal (sorted keys at every level, no whitespace).
The hash covers all SC-relevant fields: `id`, `title`,
`rationale`, `success_criteria`, `anti_goals`, `scope`,
`constraints`, `done_definition`. The hash field itself is
excluded.

Canonicalization is independent of YAML formatting quirks. Two
goals with semantically equivalent content produce the same
hash, regardless of key order or whitespace in the source file.

### 2. Lock + check

`lockGoal(goal)` — attaches `_lock_hash` to the goal object.
The hash is computed over the canonical form; the same goal
object always produces the same hash.

`checkGoalLock(goal, options)` — recomputes the hash, compares
to the stored `_lock_hash`:

- **Match**: goal is intact, return `{intact: true}`
- **Mismatch**: returns `{intact: false, reason, ...}` with a
  human-readable reason
- **Missing stored hash**: returns `{intact: false, reason:
  "no stored _lock_hash (goal never locked)"}`
- **Modes**: `audit` (default, log warning), `hard-fail` (caller
  throws), `off` (skip check entirely)

### 3. Integration

`buildLockedGoalContract(input)` — the orchestrator's create
path now produces a locked contract by default.

`goalContractToYaml` — persists the `_lock_hash` alongside the
contract fields so disk readers can verify integrity.

### Lock is INFORMATIONAL, not enforcement

The LLM could ignore the lock and proceed; the "goal_modified"
signal is captured in the audit chain. `orchestrator_audit` is
the gate; this lock is the evidence.

This is the right shape for the current architecture: the audit
already has the authority to fail the workflow. Adding a hard
fail on the LLM-side path would couple the lock to
`orchestrator_audit`'s lifecycle, which is more complex than
the current design warrants.
