# GC-2026-122 — Drop Planner auto-spawn for user intent tasks

## What happened

GC-2026-121 (merged earlier) introduced Planner auto-spawn: every user
task stamped `kind: "intent"` automatically received `agentType:
"Planner"`, and the unified feeder dispatched a Planner subagent that
called `decompose_task` autonomously. The design assumption was that
the Planner was a self-contained "intent-to-chain transformer" — it
reads the user intent from the spawn prompt and emits specs.

Empirically (observed in this session on the intent "了解一下当前仓库"
/ "get familiar with the current repo"), the Planner BLOCKed with
`PLANNER_STATUS: BLOCKED` and `toolUses: 0` — its prompt rule
(`planner.ts:65`) explicitly says to return BLOCKED for "purely
conversational / informational" intents. Because the Planner's prompt
forbids any repo exploration (`no AFT search, no codebase_memory_*,
no ctx_* search, no bash, no grep`), it had no way to recognize that
"了解一下当前仓库" could be turned into a chain like
`[Read README, Read AGENTS.md, Read package.json, Summarize]`. It
just BLOCKed and exited. The user task was left `pending` forever
with no consumer.

## Root cause

The Planner was designed as a **constrained, pattern-matching
function** that pattern-matches user-intent text against a small
allowlist of behaviors. The information it has access to is:

- The literal user-intent string (subject + description)
- A set of 4 BLOCK rules (vague / informational / > 20 specs / can't
  derive file paths)

The information it **does not have** access to:

- The project context (README, AGENTS.md, package.json, file tree)
- The repository state (which files exist, what they contain)
- The conversation history
- The agent's own judgment ("could this be turned into a chain?")

The GC-2026-121 design was sound for the "narrow, mechanically-
decomposable" case (e.g. "Refactor X, run tests, update docs") but
silently dropped every intent that required context-aware reasoning.
That's a much larger class of intents than the design assumed.

A second, related bug surfaced during the implementation review: the
existing D6 decomposition reminder (GC-2026-120 AC5) used
`ctx.ui.notify(...)` to surface pending intent tasks. `ctx.ui.notify`
is a UI-level toast — the LLM does not see it. So even when the
reminder fired, the LLM was not informed. Without fixing this, dropping
the Planner auto-spawn would have left intent tasks with **no consumer
at all** (worse than the pre-GC state).

## Fix

GC-2026-122 reverses both:

1. **`TaskStore.create` / `inferKind`** no longer stamps
   `agentType: "Planner"` on intent tasks. `kind: "intent"` and
   `requires_decomposition: true` stay as semantic markers, but the
   task is no longer auto-feedable. The main LLM is the sole consumer.

2. **`isFeedableTask`** is tightened: a task is feedable iff it has an
   explicit `agentType`. The `kind: "intent"` short-circuit added in
   GC-2026-121 follow-up is removed. Tasks persisted to disk before
   this GC may still carry `agentType: "Planner"` and remain
   feedable — that's the correct behavior for pre-existing intent
   tasks with an explicit dispatcher.

3. **`pi-tasks/src/intent-reminder.ts`** (new) exports
   `composeIntentReminder(store, state)` and
   `applyIntentReminderToSystemPrompt(store, state, existing)`. The
   first composes the reminder text (per-intent dedup via a `Set`).
   The second returns the `{ systemPrompt }` payload for the
   `before_agent_start` handler, appending the reminder to the
   existing system prompt with a `---` separator.

4. **`pi.on("before_agent_start", ...)`** now returns
   `{ systemPrompt: <existing> + <reminder> }` when there's a new
   pending intent (mirrors the orchestrator's `SYSTEM.md` injection
   pattern at `pi-orchestrator/src/extension.ts:215-226`). The old
   `maybeFireDecompositionReminder` + `ctx.ui.notify` path is removed.

5. **`pi-subagents/src/default-agents.ts`** Planner description
   updated to read "NOT auto-spawned after GC-2026-122 — the main
   LLM dispatches it explicitly via the `Agent` tool". The Planner
   subagent itself stays registered for explicit dispatch.

The main LLM, on receiving the reminder, has three options:
- Call `decompose_task(user_task_id, specs=[...])` directly with
  well-formed specs (the common case).
- Dispatch the `Planner` subagent explicitly via the `Agent` tool if
  it wants a mechanical spec compiler (e.g. after gathering context
  itself).
- Chat-answer the user if the intent is genuinely trivial, and mark
  the task completed via `TaskUpdate`.

## Follow-ups

1. **`verify:gcdb` gate had a transient failure** on the merge commit
   because no postmortem existed yet. This is the gate's correct
   behavior — it requires a postmortem OR a carve-out for every
   merged GC. The postmortem (this file) is the resolution.

2. **Plan B (MAP MISS fallback in `subagents:completed` listener)** —
   the original `agentTaskMap.get(agentId)` returns `undefined` path
   silently bails, leaving the user task `pending` indefinitely. This
   was a parallel concern raised during the analysis but not in
   scope for GC-2026-122. Should be a separate GC against
   `pi-tasks/src/task-feeder.ts:209`.

3. **Pre-existing dirty state on `main`** was stashed during the merge
   (`stash@{0}` contains the previous session's debug probes and
   partially-completed "soft-mode mental model" GC). The stash is
   preserved; the user can pop or drop it after reviewing.

4. **Pre-existing `bun test` failures in the main repo** (typebox /
   `@earendil-works/pi-tui` / `@earendil-works/pi-coding-agent`
   missing in main-repo node_modules, vitest `vi.hoisted` /
   `importOriginal` incompatibilities) are unrelated to this GC.
   Worktree's `bun install --frozen-lockfile` resolves them; the
   main repo's install state is out of scope.

5. **Documentation updates** (`AGENTS.md`, `README.md`,
   `pi-orchestrator/skills/orchestrator/SKILL.md`) describing the
   new "intent task → main LLM decompose" flow are not part of this
   GC. The Planner's own description in `default-agents.ts` and the
   `planner.ts` header comment are updated in-repo; broader docs
   should be a separate documentation GC.
