## What happened

After GC-2026-120, user-created tasks with `kind: "intent"` (no explicit
`agentType`) sat as planning data. The before_agent_start reminder
fired per-intent (GC-2026-120 follow-up fix), prompting it to invoke
`decompose_task` itself, but the consumption still depended on
chat-driven LLM intervention. The user reported "the new task added
cannot be consumed properly" — the LLM in the parent session had to
notice the reminder, decide to call decompose_task, and supply specs.
For test workloads where the LLM never gets a chat message (or
declines to intervene), the task sat indefinitely.

## Root cause

Path B of the consumption map (see the design survey in
`pi/docs/gc-index.md` for GC-2026-121) had no agent self-consumption
path. The kind=intent semantic reserved the task as "needs
decomposition", but the de facto decomposition driver was a
chat-context LLM that might never show up.

## Fix

Add Option 1 from the design survey: every `kind: "intent"` task
auto-stamps `agentType: "Planner"` in `TaskStore.create()`. The
unified feeder (already in place from GC-2026-108 / 113 / 117) sees
`isFeedableTask = true` and auto-spawns the Planner subagent.
Planner's job is one tool call: `decompose_task(user_task_id, specs)`.
The orchestrator then materializes the chain and runs it serially.

Three files change, two packages:

- `pi-tasks/src/task-store.ts`: `inferKind()` sets `agentType: "Planner"`
  when it infers `kind: "intent"`. Explicit `agentType` from the caller
  wins (so callers can override — e.g., `kind: "intent"` with
  `agentType: "Explore"` still spawns Explore).
- `pi-tasks/src/index.ts`: spawn callback refuses gracefully when
  `subagentsAvailable === false` (logs + reverts task to pending;
  before_agent_start reminder takes over). For Planner, the spawn
  prompt prepends `Task ID: <id>` so Planner can pass it to
  decompose_task without an extra lookup.
- `pi-subagents/src/default-agents.ts`: registers the `Planner`
  agent type with a narrow read-only surface (`builtinToolNames:
  ["read"]`, `extensions: ["pi-orchestrator"]` for decompose_task only,
  no AFT / codebase-memory / ctx-search). `excludeExtensions:
  ["pi-subagents"]` keeps Planner from recursively dispatching.
- `pi-subagents/src/agent-prompts/planner.ts`: the system prompt
  declares role, decompose_task contract, PLANNER_STATUS: BLOCKED
  escape hatch, and forbids exploration / file modification.

## What did NOT change

- `metadata.created_by` (still binary: `orchestrator` | `user`).
- The chat-driven `decompose_task` LLM tool (Planner uses it as-is).
- The cascade semantics in `task-feeder.ts`.
- The existing `before_agent_start` reminder (still fires for any
  intent tasks that didn't auto-spawn successfully, e.g., when
  pi-subagents isn't loaded).
- `workflow-graph.ts` / `workflow-handler.ts` / `orchestrator-task.ts`.
- AGENTS.md / README.md / SKILL.md (deferred to doc follow-up).

## Process notes

This GC shipped via the orchestrator's direct-takeover path (same as
GC-2026-120). workflow_run failed at the entry point with the same
"extensions not registered" error documented in
`pi/docs/postmortem/GC-2026-task-feeding-and-decomposition.md` —
the active session's pi runtime does not pick up the symlinked
package state. Per the soft-mode manual-takeover contract, the
orchestrator main agent implemented all 5 commits in the main
session. Pre-commit hooks (`bun test` + `verify:all`) ran on
every commit and surfaced a stale `subagent.json` catalog after
the Planner registration — fixed by running `bun run gen:catalog`.

## Follow-ups

- Doc GC: update AGENTS.md / README.md to document the Planner
  agent and the new consumption path (kind=intent → Planner →
  decompose_task → chain).
- Manual-takeover formalization (same as the GC-2026-120
  follow-up): a `manual-takeover` workflow_run mode for GCs that
  touch multiple `pi-*` packages — saves a round-trip when the
  dispatch path is broken.
- Planner benchmarking: a single Planner run + chain materialization
  currently costs two subagent spawns (Planner + T1). A future GC
  could merge Planner's tool call into the chain materialization
  path directly (Planner subagent becomes a synchronous pre-step),
  saving one round-trip on the cold path.
- `--no-auto-planner` opt-out: users who want the old chat-driven
  behavior can opt out by setting `metadata.kind: "intent"` + a
  marker (e.g., `requires_decomposition: false`) on the task. Not
  shipped now to keep the design minimal; revisit if any user
  reports Planner misbehaving.
