# GC-2026-063 — pi-evaluator agentic metrics layer (7 metrics, 0.2.0 → 0.3.0)

> **Date:** 2026-08-23
> **Status:** Resolved
> **Severity:** major (functional gap in v0.2.0 — `eval_score()` returned all-zero)

## What happened

`@sages/pi-evaluator` v0.2.0 shipped 2 tool scaffolds (`eval_score`, `eval_trend`) but the underlying scoring engine was **not implemented**. The `computeEvalScore` function read `state.active_workflow` (always `null`) and returned five `{score: 0, evidence: []}` dimensions regardless of what artifacts existed under `.pi/orchestrator/`. Every call to `eval_score()` returned the same not-yet-observed shape — a permanent false signal of "the workflow is failing."

The coefficients file declared 18+ signal names in `DEFAULT_COEFFICIENTS` but no signal readers populated them. The orchestrator's claim "reward mode gives you self-evaluation" was true only for the tool surface, not for the scoring surface. Users could turn on reward mode and see the structured output, but the numbers never moved.

There was a previous Python implementation of pi-evaluator (`1c75e17 feat: implement pi-evaluator for Four Sages workflow evaluation`) that used HuggingFace evaluate for quantitative metrics (`CodeEval`/`TextQuality`/`Security`). The July pivot to TypeScript (`760be74 chore(pi-evaluator): foundation cleanup for reward mode extension`) deleted the Python engine entirely and replaced it with the empty scaffold. The engine was the part that was lost in the pivot.

## Root cause

The pivot was a **strict contraction with no engine work** — the GC-2026-019 spec listed 2 tool surfaces + a scoring-shape contract, but treated the scoring engine as a follow-up T3 task that never shipped. T3 was deferred so long that the "scoring is wired, just call `eval_score()`" mental model became load-bearing for downstream work (e.g. agentic-metric dashboards).

The structural reason: there was no clearly-named home for the engine. `src/tools/eval-score.ts` mixed "compute the score" with "wrap it in `{content, details}` for the ToolDefinition shape." The split into pure compute + tool factory happened in GC-2026-019, but neither side reached `scoreWorkflow()` — that function didn't exist anywhere in the codebase.

## Fix

GC-2026-063 shipped the full engine layer + 7 metrics in 10 commits:

- **T1** — `Metric<I>` interface, `MetricRegistry` (idempotent register), `signal-runner.computeSignalValue`, `scoring-engine.scoreWorkflow`, coefficient-schema's additive `with?: Record<string, unknown>` (0.2.0 files still parse), `EvalState.active_workflow_path`, `computeEvalScore` becomes async with a lazy self-cook path.
- **T2** — 3 pure heuristic metrics: `step_efficiency` (coordination), `argument_correctness` (implement), `plan_adherence` (dag).
- **T3** — 2 hybrid heuristic+LLM-stub metrics: `goal_accuracy` (audit), `task_completion` (implement). Mockable seam (`setJudgeFn`) lets tests substitute the judge without mocking `pi-ai`.
- **T4** — Real `defaultJudgeFn` wrapping `complete()` from `@mariozechner/pi-ai` through the seam; 2 pure-LLM metrics `plan_quality` (dag) + `tool_use` (coordination); `parseJudgeReply` tolerates 4 reply shapes.
- **T5** — `fixtures/workflow-scoring-1/` (6 artifacts + session.jsonl with 3 task windows); `scoring-pipeline.test.ts` (8 end-to-end tests asserting per-dim scores ± tolerance); `heuristic-benchmark.test.ts` (<500ms heuristic path; actually averages **2.3ms**).
- **T6** — SKILL.md documents all 7 metrics in a table; CHANGELOG.md 0.3.0 entry; `examples/evaluator-log/coefficients.json` bumped to `0.3.0` with disabled placeholders + opt-in example.

**Backward compat:** `coefficients-backward-compat.test.ts` proves a 0.2.0 fixture file (no `with` field) parses cleanly. The new `with` field is additive + Optional.

**Cost gate:** All 7 metrics ship at `weight: 0` by default → **zero LLM tokens consumed**. Opt-in via coefficient override + `with.from = 'llm'`. Missing API key returns `data_missing: true` gracefully; hybrid metrics fall back to heuristic, pure-LLM metrics contribute nothing.

## Lesson

**A pivot that deletes the working engine layer needs to rebuild it before declaring victory.** GC-2026-019 contracted pi-evaluator from Python+HF evaluate to TS scaffold. The contraction was the right call (leaner surface, Sages-native types) but it left the engine missing, and the missing engine was load-bearing for the entire reward mode's value proposition. Two minor follow-ups would have caught this:
- A "verified-outputs" check that asserts `eval_score()` returns non-zero scores on the canonical `fixtures/workflow-good/` after the pivot ships.
- A documented `Score=0` semantic check (score-0 means "not yet observed") to distinguish "engine not wired" from "engine ran and found zero evidence."

Both checks now exist in GC-2026-063: `integration/scoring-pipeline.test.ts` asserts non-zero scores per dim, and SKILL.md's "Score 0 vs no data" section explicitly documents the convention. Future pivots should ship the engine + tests in the same commit series, not defer to T3.
