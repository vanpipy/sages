# GC-2026-056 — verification_cmd linter

> **Date:** 2026-08-20
> **Status:** Resolved
> **Severity:** major

## What happened

`goal_contract_create` previously validated that
`verification_cmd` was a non-empty string (a 5-character minimum)
but never actually ran the command. The LLM could submit
`echo "yes"` or any other tautology, and the orchestrator
accepted it as a "verifiable" success criterion.

This gap meant: at the END of a workflow, `orchestrator_audit`
could report PASS because all `verification_cmd`s PASS — even
though those commands were no-ops from the start. The audit's
surface signal was meaningless against placeholder commands.

The user explicitly identified this as a concern during the
session that produced this GC. The 4-phase plan from the design
discussion listed "verification_cmd linter" as a Tier-3 concern.

## Root cause

`validateGoalContract` (the synchronous validation in
`pi/src/tools/orchestrator/goal-contract.ts`) checks the format
of `verification_cmd` (non-empty, ≥ 5 chars) but not its
semantics. The orchestrator_audit phase runs the commands and
checks exit codes — a `true` or `echo "yes"` returns 0 cleanly,
and the audit reports PASS.

The LLM's incentive: write the cheapest possible verification
command to satisfy the goal contract. The result: the goal
contract is technically valid but the workflow has no actual
verification surface.

## Fix

New module `pi/src/tools/orchestrator/verification-cmd-linter.ts`
with two layers of defense:

### 1. Heuristics (sync, primary gate)

`isPlaceholderVerificationCmd(cmd: string): boolean`:

- Empty / whitespace-only
- Single-token no-ops: `true`, `false`, `:`, `exit 0`, `cd .`, `cd /`
- Echo with placeholder argument: `yes`, `ok`, `done`, `pass`,
  `failed`, `placeholder`, `todo`, `fixme`, `1`, `0`, `true`, etc.
  (29 documented placeholder forms)
- Bare `echo` (no argument)

Returns false for any command that looks like real work
(pwd, real test commands, multi-token commands, etc.).

### 2. Execution probe (async, optional)

`runVerificationProbe(cmd, options): Promise<VerificationProbeResult>`:

- Spawns the command in a sandboxed subprocess with a 30s timeout
- SIGTERM at `timeoutMs`, then SIGKILL after a 1s grace period
- Force-resolves the promise after the grace period even if the
  child's `close` event never fires (some commands ignore SIGTERM
  and only die on SIGKILL)
- Captures stdout + stderr (truncated at 4 KiB)
- Reports `meaningful=false` when:
  - exit 0 AND no output (suspicious — verifier should produce
    observable signal)
  - spawn failed
  - timed out

### Integration

`validateGoalContractWithVerifierLinter(input)` wraps the existing
`validateGoalContract` and adds the heuristic check on each SC's
`verification_cmd`. The LLM cannot create a goal with placeholder
verification_cmds.

The probe is exposed as a separate async function (`runVerificationProbe`)
for callers that want the deeper check. We don't run it
unconditionally at goal creation because:
- Goal creation must be synchronous and fast (the LLM's tool call)
- Some verifications are stateful (e.g. `git status`) and not
  meaningful at goal-creation time anyway
