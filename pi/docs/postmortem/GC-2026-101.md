# GC-2026-101 — Postmortem

## What happened

`install.sh` gains a fifth mode: `--sync-only`. It force-copies the
pi-orchestrator + pi-tasks source files into `$PKG_DIR` without
re-running bun install, the npm peer setup, SYSTEM.md, the pi CLI
install, or any other peer. The fast path on top of a complete
install — for shipping a one-commit source fix to a running pi
session without the 90s+ full reinstall.

This closes the follow-up flagged by two earlier GCs:
`GC-2026-pi-tasks-cascade-agentid` and `GC-2026-boundary-subagent-control`.
Both noted that after a source-only fix (e.g., a workflow handler
patch), the only path to ship it to a running pi session was `--force`
which reinstalls everything: ~90s of bun install + an AFT binary
re-download. The fast path is the obvious answer; it just hadn't been
written.

## Root cause

`install.sh` already had three orthogonal modes (`--uninstall`,
`--orchestrator-only`, `--system-only`) and an arg parser with
mutual-exclusion. Adding a fourth was a routine extension.

The non-routine part: `PI_TASKS_DEST_DIR` was computed at script entry
from the initial `PI_DIR`, and `--prefix` only re-derived `PI_DIR` +
`PKG_DIR`. When the user passed `--sync-only --prefix /tmp/test`,
`PI_TASKS_DEST_DIR` kept its entry-time value (`$HOME/.pi/packages/pi-tasks`)
and the `cp -r` wrote to the wrong location. Found this with a smoke
test in `/tmp/sages-test-install/` before merging.

## Fix

### 1. `install.sh` — `install_sync_only()` function

```bash
install_sync_only() {
  # Pre-flight: refuse to run if runtime isn't installed
  if [[ ! -d "$PKG_DIR" ]]; then
    echo "  Error: $PKG_DIR does not exist; sync-only needs a prior full install"
    ...
  fi
  if [[ ! -d "$PI_TASKS_DEST_DIR" ]]; then
    echo "  Error: $PI_TASKS_DEST_DIR does not exist; sync-only needs pi-tasks installed"
    ...
  fi

  # Force-copy orchestrator source directories (no SKIP-if-exists check)
  for dir in skills src templates; do
    [[ ! -d "$LOCAL_REPO_ROOT/pi-orchestrator/$dir" ]] && continue
    rm -rf "$PKG_DIR/$dir"
    cp -r "$LOCAL_REPO_ROOT/pi-orchestrator/$dir" "$PKG_DIR/$dir"
    echo "  Synced $dir/"
  done
  cp "$LOCAL_REPO_ROOT/pi-orchestrator/package.json" "$PKG_DIR/package.json" \
    && echo "  Synced package.json (deps preserved; bun install NOT re-run)"

  # Force-copy pi-tasks source directories (no node_modules)
  if [[ -d "$LOCAL_REPO_ROOT/$PI_TASKS_SRC_REL" ]]; then
    rm -rf "$PI_TASKS_DEST_DIR/src" "$PI_TASKS_DEST_DIR/test" "$PI_TASKS_DEST_DIR/skills"
    cp -r "$LOCAL_REPO_ROOT/$PI_TASKS_SRC_REL/src" "$PI_TASKS_DEST_DIR/src"
    cp -r "$LOCAL_REPO_ROOT/$PI_TASKS_SRC_REL/test" "$PI_TASKS_DEST_DIR/test"
    [[ -d "$LOCAL_REPO_ROOT/$PI_TASKS_SRC_REL/skills" ]] \
      && cp -r "$LOCAL_REPO_ROOT/$PI_TASKS_SRC_REL/skills" "$PI_TASKS_DEST_DIR/skills"
    echo "  Synced pi-tasks src/ + test/ + skills/ (deps preserved)"
  fi
}
```

### 2. `install.sh` — arg parser + mutual exclusion

```bash
local ... SYNC_ONLY=false

--sync-only) SYNC_ONLY=true; MODE_COUNT=$((MODE_COUNT+1)); shift ;;

if [[ "$MODE_COUNT" -gt 1 ]]; then
  echo "Error: --uninstall, --orchestrator-only, --system-only, --sync-only are mutually exclusive"
  ...
elif $SYNC_ONLY; then
  install_sync_only
```

### 3. `install.sh` — `--prefix` re-syncs `PI_TASKS_DEST_DIR`

```bash
--prefix)
  PI_DIR="$2"
  PKG_DIR="$PI_DIR/packages/$PKG_NAME"
  PI_TASKS_DEST_DIR="$PI_DIR/packages/pi-tasks"
  PI_TASKS_PKG="$PI_TASKS_DEST_DIR"
  shift 2
  ;;
```

Without this, `--sync-only --prefix /tmp/test` would `cp` into
`$HOME/.pi/packages/pi-tasks` and silently skip `/tmp/test/packages/pi-tasks`.

### 4. `install.sh` — usage text + header doc comment

```
--sync-only        Force-copy pi-orchestrator + pi-tasks source files only
                   (no bun install / no peer setup / no SYSTEM.md / no pi CLI).
                   Requires a prior full install on the same prefix.

Modes are mutually exclusive: pick one of (default | --uninstall | --orchestrator-only | --system-only | --sync-only).
```

## Behavior change (deliberate)

Adds a new mode (`--sync-only`). The four existing modes
(`--uninstall`, `--orchestrator-only`, `--system-only`, default full
install) behave exactly as before.

The `--prefix` flag now also re-syncs `PI_TASKS_DEST_DIR`. This is a
**bug fix** for a pre-existing latent bug (previously `--prefix
/tmp/test` wrote pi-orchestrator files to `/tmp/test` but pi-tasks
files to `~/.pi`); the bug was unreachable because no existing flag
combined `--prefix` with the pi-tasks install path.

## Lessons

1. **Two flag combinations that have never been tested are a latent
   bug source.** `--prefix` had not been combined with `--sync-only`
   because the latter didn't exist; `--prefix` had not been combined
   with the pi-tasks install path because no flag exercised it. Adding
   a new flag that crosses both surfaces forces the smoke test to
   catch the stale-variable bug. The right pattern for additive
   install modes: every new flag should be paired with every existing
   flag in a smoke matrix.

2. **The fast-path install mode should refuse to run on a fresh
   prefix.** `--sync-only` does not install dependencies, peer
   packages, the pi CLI, or anything else. Running it on a system
   that hasn't been through the full install produces a broken
   runtime — the failure would surface only when the user starts pi
   and gets `Cannot find module 'js-yaml'`. The pre-flight checks
   (`[[ ! -d "$PKG_DIR" ]]` / `[[ ! -d "$PI_TASKS_DEST_DIR" ]]`) plus
   a clear "run full install first" message push that failure to
   install-time, where it's actionable.

3. **`set -e` + `cp -r` is silent on the wrong-source-path case.**
   `cp -r /missing/path /dest` succeeds (creates an empty `/dest`),
   not error. The fix is to test `-d` on the source before `cp`, or to
   pair every `cp` with a follow-up assertion that the destination has
   the expected files. The smoke test caught this when I ran it
   manually before merging.
