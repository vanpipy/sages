# GC-2026-059 — L1 advisory chain-key detection (mirror dsh)

> **Date:** 2026-08-20
> **Status:** Resolved
> **Severity:** minor

## What happened

L1 advisory's `dag_resynth_loop` rule used a **per-goal_id counter**
as a partial chain-key. A model that legitimately refines a goal
(different args on each `dag_synthesize` call) was flagged as
"stuck" after 3 calls — a false positive.

Similarly, `no_progress_no_audit` used a global count: any 10+
tool calls triggered the rule regardless of pattern, which
produced noise in normal use (any substantial workflow involves
10+ tool calls).

## Root cause

Pre-GC-2026-059, the L1 detectors used **per-tool or per-goal_id
counters** that didn't account for argument identity. `dag_synthesize
called 3 times for goal GC-1` and `dag_synthesize called 3 times
with identical args` triggered the same rule, even though the
first case is a model refining the goal (progress!) and the second
is a model stuck on the same call (regression).

dsh's `repeat-tool-reminder` solves this with **chain-keys**: a
stable key derived from `(toolName, canonicalized-args)`. Two calls
produce the same key iff their args are semantically equivalent.
Counting identical chain-keys (not just call types) gives the
"stuck" semantics the rule is actually trying to detect.

## Fix

GC-2026-059 adopts the chain-key pattern. Two surface changes:

1. **`dag_resynth_loop` switched from per-goal counter to full
   chain-key.** 3+ calls with identical args fire; refinement
   (different args) does NOT.

2. **`no_progress_no_audit` tightened to require a chain at
   length >= 3.** Without the chain-key, the rule fired on any
   10+ tool calls regardless of repetition. Now it requires
   both: many calls AND a pattern.

Plus a **new rule `repeat_call_chain`**: general "stuck on same
call" detector, mirrors dsh's `repeat-tool-reminder`. Fires when
any (tool, args) chain-key is at length >= 3. Suppressed when the
worst chain is `dag_synthesize` (already covered by the more
specific `dag_resynth_loop`).

### Module: `chain-key.ts`

A new helper module with 4 exports:

- `canonicalJSON(value)` — recursive key-sort + JSON.stringify.
  Two objects with semantically equivalent content produce the
  same canonical string regardless of key order.
- `chainKey(toolName, args)` — `${toolName}::${canonicalJSON(args)}`.
- `tallyChainCounts(calls)` — Map<key, ChainCount> with count + sample.
- `findMaxChain(counts)` / `chainCountAtLeast(counts, threshold)` —
  helpers for downstream rules.

### Module: `l1-advisory.ts`

Refactored. The 5 original rules' surface contract unchanged
(same rule ids, severities, fixdirective text). Internal detection
logic now uses chain-key for the two rules where it actually helps.

### False-positive reduction

| Scenario | Pre-2026-059 | Post-2026-059 |
|---|---|---|
| 3× `dag_synthesize` same goal, different args (refinement) | **fires** (false positive) | silent |
| 3× `dag_synthesize` same goal, identical args (stuck) | fires | fires |
| 12× distinct `read` calls without audit | **fires** (false positive) | silent |
| 12× `read` calls with 3+ reads of same path, no audit | fires | fires |
| 3× `read` of same path | (no rule) | **fires** (`repeat_call_chain`) |

## Anti-port

The full dsh `repeat-tool-reminder` design has additional features
that we **deliberately did not port**:

- `include`/`exclude` patterns with `*` wildcards
- Per-agent `WeakMap` keying
- `runtime-diagnostics` integration
- Multiple thresholds `[3, 5, 8]` with escalating reminder text
- Argument preview character cap

These are designed for a full agent harness with many tools and
many agents. Sages is a thin orchestrator with 4-5 tools and
typically one main agent. Adding the full machinery would be
over-engineering. We adopt the chain-key mechanic (the core
innovation) but stop there.

## Follow-ups

- Real-world false-positive rate measurement: run a few real
  orchestrations, count how many `dag_resynth_loop` advisories
  fire. If the rate drops as predicted (~50%), the change is
  validated. If false positives are still common, revisit the
  threshold or add a per-agent dedup layer.
- Consider per-agent keying if multiple LLM agents ever run
  concurrently (e.g. parallel developer dispatches). The current
  `tallyChainCounts` is global to the orchestrator session.
- The `repeat_call_chain` thresholds (currently hard-coded to
  3) could become profile-configurable. Defer until real
  thresholds are observed.
