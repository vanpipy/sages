# GC-2026-081 — Expose todowrite* in the orchestrator active toolset

## What happened

`pi-orchestrator/src/extension.ts:175-181` (the `session_start` hook) called
`pi.setActiveTools([...ORCHESTRATOR_TOOLS, ...SUBAGENT_TOOLS, ...BASELINE_TOOLS])`
— a strict 15-tool allowlist. Three `todowrite*` tools were registered with
pi but excluded from this list:

1. `todowrite` — registered by `@cortexkit/pi-magic-context` at extension boot (default enabled; see `~/.pi/agent/npm/node_modules/@cortexkit/pi-magic-context/dist/index-zxgbtsnj.js:53565`).
2. `todowrite_compile` + `todowrite_progress` — registered by the orchestrator's `registerTodowriteTools(pi)` at `extension.ts:152` (GC-2026-074).

Meanwhile the orchestrator's constitution (`pi-orchestrator/templates/SYSTEM.md` lines 17-19, 128-129, 152, 154) repeatedly directed the LLM to use these tools for tracking multi-step work and reconciling DAG↔todo drift. The directive advertised tools the runtime hid.

Empirically surfaced during GC-2026-076: an 8-SC / 2-task DAG ran end-to-end with zero `todowrite` activity. The orchestrator's `extractAuditFindings` machinery in `pi-subagents/src/agent-runner.ts:2213` is built around the YAML-block schema the runtime prompt never told the agent to emit, so `missing_yaml_block` fired on every dispatch. The agent never had the option to call `todowrite` — the LLM schema didn't include it.

## Root cause

`setActiveTools` is a strict allowlist (pi-coding-agent's denotational contract:
only listed tools are visible to the LLM). The session_start hook curates
exactly which tools the LLM sees, and the curate omitted every `todowrite*`
tool even though two separate extensions had registered them. The constitution
in `templates/SYSTEM.md` was correct ("use `todowrite` for >2 items"); the
runtime gate was wrong (allowlist didn't include `todowrite`).

The drift between constitution and runtime slipped through review because:

1. The 5 orchestrator tools + 3 subagent tools + 7 baseline FS tools were
   sufficient for the historical 15-tool session; the GC-2026-074
   todowrite-view work was treated as a documentation-only addition.
2. The system prompt + the runtime gate are reviewed independently — no
   verifier cross-checks that every tool the constitution mentions is in
   the active toolset.
3. The bug only manifests as a missing tool schema in the LLM's context.
   Nothing crashes; nothing logs an error; the LLM just doesn't know the
   tool exists.

## Fix

Added `TODOWRITE_TOOLS` constant at `pi-orchestrator/src/extension.ts:112`:

```typescript
export const TODOWRITE_TOOLS: readonly string[] = [
    "todowrite",
    "todowrite_compile",
    "todowrite_progress",
];
```

Spread it into the `session_start` `setActiveTools` array at extension.ts:175-181:

```typescript
const tools: string[] = [
    ...ORCHESTRATOR_TOOLS,
    ...SUBAGENT_TOOLS,
    ...BASELINE_TOOLS,
    ...TODOWRITE_TOOLS,  // GC-2026-081
];
pi.setActiveTools(tools);
```

The existing 15 tools remain in the active set; the new constant adds 3 more
for a total of 18. Existing ORCHESTRATOR/SUBAGENT/BASELINE constants were
also exported (so the test could pin their contents).

New test file at `pi-orchestrator/test/extension-active-tools.test.ts`
(166 lines, 12 tests):

- 3 SC tests asserting the TODOWRITE_TOOLS array literal contains the 3 tool names.
- 3 regression tests asserting the existing ORCHESTRATOR/SUBAGENT/BASELINE arrays still contain their original tool sets.
- 5 source-text-scan tests asserting the session_start hook literal spreads all four arrays and calls setActiveTools.
- 1 end-to-end `MockPi` test that actually fires the session_start handler and asserts the exact 18-entry list (the strongest pin).

Single commit on `sages/GC-2026-081/P1`:

## Process observations

The dispatched developer sub-agent hit its 200-turn ceiling while writing the per-task HANDOFF.md — the third consecutive GC where the agent's code work + verification ran cleanly but the meta-tasks (HANDOFF.md, YAML block, audit file) hit the turn limit. This is a recurring pattern; the recommendation from GC-2026-076's postmortem was "tighten auditor scope", but the developer is the actual runaway. The fix likely needs to:

1. Make the meta-tasks (HANDOFF.md, YAML block) the FIRST thing the agent does after commit, not the LAST.
2. Allocate a strict per-phase turn budget (e.g., 30 turns for code + verify, 20 turns for commit, 20 turns for meta-tasks).
3. Have the agent emit the YAML block as the LAST turn of the verify phase (not as a final message), so the orchestrator can extract it without needing the agent to also write HANDOFF.md.

For now, the pattern remains: main agent writes HANDOFF.md + audit-P1.md on the developer's behalf when the developer times out. This works but adds a step.

- **GC-2026-083 (suggested)**: add a `verify:allowlist-sync` gate that reads `extension.ts`'s exported arrays + all `pi.registerTool` calls in `*.ts` and fails if any registered tool is not in the allowlist. Cross-check on the next GC that adds a new tool.

- **Process rule (escalate)**: every GC developer sub-agent should explicitly commit BEFORE writing HANDOFF.md and BEFORE any meta-tasks. The current pattern (commit + verify + then meta-tasks) burns turns on the meta-tasks even though the deliverable is already durable in git.

## Lessons

1. **Constitution + runtime gate need a verifier.** A constitution that mentions a tool the runtime hides is a silent bug. Add a `verify:allowlist-sync` gate (GC-2026-083) so this drift is caught mechanically.

2. **`setActiveTools` is a hard allowlist, not a default filter.** Pi-coding-agent's `setActiveTools(...)` is denotational: only listed tools are visible. Documenting this clearly in the orchestrator's extension.ts would have prevented this bug — the existing comment says "Replaces the historical `profile.tools` capability filter" but doesn't say "this is a strict allowlist, not a default filter".

3. **Schema exposure and prose mention should be checked together.** The orchestrator's SYSTEM.md mentions 18 tool names (5 + 3 + 7 + 3) — but the runtime allowlist had only 15. The two should always match. Add an allowlist-sync verifier to enforce this invariant.

4. **Meta-tasks should be early, not late.** Three consecutive GC turn-budget overruns on the meta-tasks (HANDOFF.md, audit file, YAML block) suggest the developer prompt's turn budget is exhausted by code+verify before reaching the report-writing phase. Reorder the developer prompt's checklist to commit + write HANDOFF.md + write YAML block FIRST, then run any post-commit cleanup LAST.

5. **The audit-gate machinery was correctly designed but was never given the signals it expected.** `extractAuditFindings` (`pi-subagents/src/agent-runner.ts:2213`) parses YAML blocks + checkpoint lines + ASK markup from the agent's final message — but the agent never emitted any of these because the runtime prompt never told it to. GC-2026-076 wired the runtime prompt; GC-2026-081 exposed the tool the agent needs to track itself. Together, both GCs complete the activation loop.
