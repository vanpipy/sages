# GC-2026-103 — Postmortem

## What happened

Three integration tests added on the orchestrator side that drive
the production `workflow_run ↔ subscribeWorkflow` boundary through the
real wiring. The B6 (iteration-aware review) and B7 (Merger consumes
Reviewer evidence) mechanisms were already wired in pi-tasks
(`formatPriorReviewSummary` and `writeReviewerEvidenceFile`); this GC
adds the orchestrator-side regression coverage that was missing.

## Root cause

GC-2026-verdict-states-and-dynamic-cascade added the B6 wiring
(`formatPriorReviewSummary` injected into the cascade's pre-spawn loop
when `iteration > 1 && findingsHistory.length > 0`). GC-2026-prompt-parser-
contract-cleanup added the B7 wiring (`writeReviewerEvidenceFile` writes
`.pi/orchestrator/last-review-{goal_id}.md` after every Review, plus the
Merger (Advisor) prompt reads that file).

What was missing: orchestrator-side integration tests that drive the
real `executeWorkflowRun` → `subscribeWorkflow` → `subagents:rpc:spawn`
→ `subagents:completed` → `workflow:phase-complete` chain end-to-end,
with the production shape of `randomUUID().slice(0,17)` for spawn ids.
The pi-tasks unit tests (workflow-handler.test.ts) cover the cascade
internals in isolation; the GC-2026-102 R-INT integration test covers
the happy-path 5-spawn workflow but doesn't exercise B6 (needs 2
reviews with findingsHistory) or B7 (needs to read the evidence file).

## Fix

### 1. `test/helpers/workflow-run-integration-harness.ts` (NEW)

Extracted the GC-2026-102 integration test helpers into a shared
file so both R-INT and B6/B7 tests can use them. Adds:

- `cleanReviewResult(iteration)` — CLEAN verdict YAML (with closed
  ```yaml fence — the parser requires this; missing close fence
  silently falls back to NEEDS_WORK with empty findings).
- `needsWorkReviewResult(iteration, opts)` — NEEDS_WORK verdict
  YAML with multiple findings (each carrying severity + issue +
  optional category).
- `startWorkflowRun(harness, goalId, options)` — boots a fresh
  workflow_run with the harness's pi.events and a written goal-{id}.yaml.
- `cleanupHarness(harness)` — closes the worktree + unsubscribes.

### 2. `test/tools/orchestrator/workflow-run-b6-b7.test.ts` (NEW, 3 cases)

- **B6** — a 2-review workflow where Review_1 is NEEDS_WORK (with one
  critical finding, category=new), then asserts Review_2's dispatch
  brief contains `## Prior review summary (iteration 1)` (the
  `formatPriorReviewSummary` injection) and the prior finding's text.

- **B7 #1** — a workflow that completes a NEEDS_WORK Review, then
  asserts `.pi/orchestrator/last-review-{goal_id}.md` exists in the
  worktree path (not the harness's repoCwd — `writeReviewerEvidenceFile`
  writes to `payload_worktree_path + .pi/orchestrator/...`, which is
  `<repoCwd>/.pi/worktree/<goalId>/implement/.pi/orchestrator/...`),
  with the verdict, scope/anti_goal checks, and findings[] sections
  matching the emitted Reviewer verdict.

- **B7 #2** — drives a 2-Review sequence (NEEDS_WORK then CLEAN) and
  asserts the evidence file is OVERWRITTEN on the second Review (file
  reflects verdict=CLEAN with no findings, the first review's
  "first issue" finding is gone). Confirms the "always reflects the
  latest Review" contract.

## Lessons

1. **The integration test had to use the right `completeByIndex` for
   each cascade step.** The static graph creates tasks in insertion
   order, and `writeReviewerEvidenceFile` writes to the worktree
   path (not the harness's repoCwd). Three test bugs caught during
   development:
   - Wrong spawn index (ImplementAdvisor vs Review_1)
   - Wrong path construction (harness.repoCwd vs harness.repoCwd/.pi/worktree/...)
   - Missing closing ```yaml fence (parser silently falls back to
     NEEDS_WORK with empty findings)

   Each was a 30-second fix once the test's failure message was read
   carefully. The integration test would have surfaced these if the
   wiring had a future regression.

2. **Integration tests complement unit tests.** pi-tasks's
   `workflow-handler.test.ts` has 4 tests covering B6 + B7 (each
   tests a specific scenario in isolation). The orchestrator's
   integration tests cover the wiring through the real
   `executeWorkflowRun` path — which exercises the workflow-run.ts →
   workflow-handler.ts boundary. A regression in either layer would
   show up in one or the other test.

3. **The harness helpers are now shared.** `workflow-run-integration-harness.ts`
   exports the fake-events bus, real-id subagents mock, and the
   harness factory. Future integration tests can reuse these
   without re-implementing the mock layer.
