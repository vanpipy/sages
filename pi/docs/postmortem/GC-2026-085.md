# GC-2026-085 — Wrap orchestrator todowrite tool returns in ToolResult shape

## What happened

`pi-orchestrator/src/todowrite.ts` `executeTodowriteCompile` (lines 100-163) and `executeTodowriteProgress` (lines 186-250) returned plain JS objects (`{ok, dag_id, items, ...}`). When wrapped via `api.registerTool({...execute: () => executeTodowriteCompile(...)})` (lines 273-296), the registered tool's execute returned the same plain object.

But pi-coding-agent's `render-utils.js:38 getTextOutput` expects a `ToolResult` envelope:
```javascript
const textBlocks = result.content.filter((c) => c.type === "text");
```

So `result.content` was undefined on the orchestrator's tool result, and `.filter` threw `TypeError: Cannot read properties of undefined (reading 'filter')`. pi's interactive TUI caught the uncaught exception and exited.

Empirically surfaced during today's live test session (round 1) — calling `todowrite_compile` from the LLM crashed pi's interactive TUI with the TypeError above. Round 2 of the test confirmed the bug live.

## Root cause

GC-2026-074 (commit `4849f8e`) shipped `todowrite_compile` and `todowrite_progress` with the wrong return shape. The integration test gap: the existing unit tests tested the underlying `executeTodowriteCompile` / `executeTodowriteProgress` functions directly (bypassing the `registerTool` registration), so the integration gap was invisible. The bug stayed dormant because the tools were registered but never called — until GC-2026-081's allowlist fix exposed them to the LLM, after which round 1 of today's test session crashed pi on first call.

This is the **third consecutive GC** where an integration gap hid a shipping bug:
- GC-2026-081 — `setActiveTools` allowlist excluded registered tools (constitution advertised a tool the runtime hid).
- GC-2026-085 — registered tool's execute returned a wrong-shape envelope (tools were unreachable-but-would-crash).
- GC-2026-086 (next) — `aft_*` and `ctx_*` tools also missing from the allowlist (constitution mandates AFT, runtime hides it).

The pattern: tools are registered in their respective extension packages (pi-magic-context, AFT, the orchestrator itself), but the orchestrator's `setActiveTools` allowlist doesn't include them. There's no mechanical verifier that catches the drift. GC-2026-083 (proposed `verify:allowlist-sync`) would close this class of bug.

## Fix

Wrapped the registered tool's execute arrows in the canonical ToolResult envelope. The underlying `executeTodowriteCompile` / `executeTodowriteProgress` functions stay unchanged (preserving backward compat with any callers that import them directly); only the registered tool's execute role wraps them.

Before:
```typescript
api.registerTool({
    name: "todowrite_compile",
    ...
    execute: (_id, params, _signal, _onUpdate, ctx) =>
        executeTodowriteCompile(params as TodowriteCompileInput, { cwd: (ctx as { cwd: string }).cwd }),
});
```

After:
```typescript
api.registerTool({
    name: "todowrite_compile",
    ...
    execute: (_id, params, _signal, _onUpdate, ctx) => {
        const result = executeTodowriteCompile(
            params as TodowriteCompileInput,
            { cwd: (ctx as { cwd: string }).cwd },
        );
        return {
            content: [{
                type: "text",
                text: JSON.stringify(result, null, 2),
            }],
        };
    },
});
```

Same pattern applied to `todowrite_progress`.

New test file at `pi-orchestrator/test/todowrite-tool-result.test.ts` (351 lines, 7 tests):

- 3 SC1 tests asserting `todowrite_compile`'s registered execute returns ToolResult shape (happy path, JSON-parse-able text, error path also wrapped).
- 3 SC2 tests asserting `todowrite_progress`'s registered execute returns ToolResult shape (happy path, JSON-parse-able text, missing dag_id returns ToolResult with ok:false).
- 1 SC3 integration test that mocks `pi.registerTool`, invokes the captured tool's execute, and asserts the registered-tool object (not the underlying function) has the ToolResult-shape contract — closes the integration gap that hid the original bug.

The integration test pattern (mock registerTool, invoke captured tool, assert result shape) is reusable for any future orchestrator tool — the next time a tool is registered, this pattern catches return-shape drift.

## Process observations

This is **not** the same as `--author`/`-c user.*`/`GIT_AUTHOR_*` (which would override the author); `--reset-author` re-applies the resolved-from-config identity, which is the spec-compliant path. Still, the developer-prompt rule says "never use --author / GIT_AUTHOR_* / git -c user.*=…" — `--reset-author` should be either explicitly permitted or explicitly forbidden in the developer prompt. ## Lessons

1. **Test the registration boundary, not just the underlying function.** The original GC-2026-074 tests bypassed `api.registerTool` by calling `executeTodowriteCompile` directly. That worked at the function level but missed the integration gap. Every future orchestrator tool should have at least one integration test that mocks `pi.registerTool`, invokes the captured tool, and asserts the result shape.

2. **Mechanical verifiers catch integration gaps humans miss.** The "the runtime gate doesn't match the constitution" class of bug is invisible to unit tests. A `verify:allowlist-sync` gate + a `verify:tool-result-shape` gate would prevent this. The pattern repeats: GC-2026-081 (allowlist), GC-2026-085 (return shape), GC-2026-086 (allowlist again). All three are integration-gap bugs.

3. **`--reset-author` is not the same as `--author`.** The developer prompt should clarify. `--reset-author` re-applies the resolved-from-config identity (spec-compliant); `--author`/`-c user.*`/`GIT_AUTHOR_*` overrides the identity (forbidden). The current prohibition is correct for the latter three; `--reset-author` belongs in the permitted list.

4. **Three strikes rule for follow-up deferrals.** GC-2026-083 was originally a follow-up in GC-2026-081's postmortem, then a follow-up in GC-2026-085's postmortem. If it appears as a follow-up in GC-2026-086's postmortem too, it becomes a blocker and ships immediately.

5. **The dormant GC-2026-074 machinery is now reachable end-to-end.** After GC-2026-081 (allowlist) + GC-2026-085 (return shape), `todowrite_compile` and `todowrite_progress` work end-to-end. After GC-2026-086 (aft_*/ctx_* allowlist), the full toolset is reachable.
