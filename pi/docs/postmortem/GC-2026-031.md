# GC-2026-031 — Soft mode + task-count threshold

> **Date:** 2026-08-06
> **Status:** Resolved
> **Severity:** major

## What happened

Sages shipped with a hard-mode toggle: the bash-guard and file-gate
were configured to **block** any tool call that matched their
respective L1–L4 rules. Layer 1 (read-only) and Layer 2 (git-meta)
were advisory; Layer 3 (meta-file write) and Layer 4 (production-code
write) returned `BLOCKED:` and refused the call.

The intent was to enforce Red Line #1 mechanically. The reality was
that the gate tripped during routine operations:

- `rm` / `mv` / `cp` inside a temporary scratch directory under
  `/tmp/sages-*/ws-*/` was blocked because the path classifier
  treated the temp tree as a meta-file write.
- Editing a one-line README typo in the root `package.json` was blocked
  even though the user's intent was a trivial cosmetic fix.
- Spawning an `Explore` agent inside a peer package was blocked because
  the L3 classifier interpreted "agent prompt mentions `pi-*/`" as
  production-code intent.

Users who wanted to do focused, time-pressured work on a non-production
surface were forced to either disable the gate globally (losing the
protection) or work around it with cryptic `safe-write` shell prefixes.
Neither was acceptable for a productivity tool.

## Root cause

The policy enforcement was **conflated** with the productivity
affordances. The bash-guard had no soft-fail mechanism: it could only
allow or block, with no in-between state that surfaced the rule while
still letting the work proceed.

There was also no escape hatch for the **task-count threshold** case.
A 1-line edit is genuinely a different shape from a 5-file refactor,
and the gate treated them identically.

## Fix

GC-2026-031 introduced **soft mode**:

- Full tool access by default — nothing is mechanically blocked.
  `rm` / `mv` / `cp` / `unlink` / `rmdir` all flow through the
  classifier but the classifier returns `advisory` instead of `block`.
- The bash-guard classifier detects write-intent bash calls and the
  extension appends a once-per-session system reminder via
  `pi.appendEntry("system", SOFT_MODE_REMINDER)`. The reminder is
  goal-orientation — it nudges back toward staying aligned with the
  goal — it does not flag specific write actions as "production code".
- The **task-count threshold** drives the recommended pattern:
  - `todowrite` has **> 2 items** → recommend the 4-stage DAG workflow
    (`goal_contract_create` → `dag_synthesize` → `task_dispatch` →
    `orchestrator_audit`), or dispatch `developer` with managed-worktree
    isolation.
  - `todowrite` has **≤ 2 items** → direct handling with `edit` /
    `write` / `bash` in the main session is acceptable. No DAG required.

Drift from the recommended pattern is auto-steered (the bash-guard
classifier), never blocked. Soft mode is the **only** mode — there is
no previous-enforcement toggle (no hard-mode toggle, no path gate).

## Follow-ups

- **Replaced by GC-2026-049** (profile / bundle composition) for
  finer-grained control. Soft mode still exists as the default
  baseline; GC-2026-049 layered the `light` / `standard` /
  `audit-strict` / `ci-only` profile system on top so users can pick
  a stricter mode without losing the soft-mode baseline.
- A periodic review of `SOFT_MODE_REMINDER` wording — the system
  prompt suffix appended via `before_agent_start` should evolve with
  the most common failure mode observed in worker artifacts.
