# GC-2026-098 — Postmortem

## What happened

Three pre-existing test failures closed in one commit; all three are
test-fixture or source-drift issues, no runtime behavior change. The
failures had been documented as "pre-existing" in the
`GC-2026-pi-tasks-test-compat` postmortem (closes 10 of 12) and the
subsequent drift-sweep GCs, but never actually fixed. Closing them
was the Batch A prerequisite for the planned GC-2026-102 (workflow_run
finalize) integration tests, which would inherit the same false
negatives if left in place.

| # | File | Category | Pre-existing since |
|---|---|---|---|
| 1 | `pi-tasks/test/path-b-e2e.test.ts` | test-fixture id collision | introduced by `GC-2026-pi-tasks-cascade-agentid` (2026-10-02); surfaced as test fail after the test fixture was added but the slice-truncation bug went unnoticed |
| 2 | `pi-tasks/test/workflow-handler.test.ts` | sync emit + await mismatch | added in `GC-2026-workflow-chat-stream` (2026-10-04) — the test passed once when the cascade happened to drain within one tick; became unreliable after later async additions |
| 3 | `pi-subagents/test/agent-runner-boundary-survival.test.ts` | source removed, test kept | `GC-2026-subagent-time-only-limits` (2026-10-04) deleted `SOFT_LIMIT_STEER_MESSAGE`; the test pinning it never updated |

## Root cause

Three coupled patterns:

- **A. Test fixtures that mirror production shapes via shorthand.** The
  real-id spawn fixture (`path-b-e2e.test.ts:372`) tried to mirror
  pi-subagents's `randomUUID().slice(0, 17)` shape but used a
  counter-based string with `.slice(0, 17)`. Production uses truly
  random ids, so the slice truncation is invisible there; in the test,
  once the counter hit 10, the slice dropped the differentiating digit
  and every subsequent spawn shared one agentId. `agentToTask.set`
  kept overwriting itself, the cascade broke, and the second test in
  the describe block failed silently.

- **B. Async cascade drained under one `setImmediate`.** The
  workflow-handler test (`workflow-handler.test.ts:808`) called
  `events.emit(...)` without awaiting and read the spawnAgent mock
  after one `flush()` (a single `setImmediate` tick). The cascade
  chain is multi-await (`await spawnAgent → await store.update`),
  so on most runs the spawn for `Review_1` hadn't run yet when the
  assertion fired. The test passed once by coincidence when the
  cascade happened to drain within the tick — flaky.

- **C. Source removal without test cleanup.** `SOFT_LIMIT_STEER_MESSAGE`
  was removed by `GC-2026-subagent-time-only-limits` in favor of the
  wall-clock deadline envelope + the `verdict-{task_id}.md`
  file-fallback pattern (which agents invoke explicitly in their
  prompt rather than relying on a runtime nudge). The source comment
  at `pi-subagents/src/agent-runner.ts:177` documents the removal,
  but the test pinning the runtime contract was kept and has been
  failing on main since. Pure drift, no production impact.

## Fix

One commit (`be3353a test(pi-tasks+pi-subagents): close 5 pre-existing test fails (GC-2026-098)`),
three files:

### 1. `pi-tasks/test/path-b-e2e.test.ts` — randomUUID + per-test isolation

```diff
- let idCounter = 0;
- const realIds = new Map<string, string>();
- const realId = `cf9f3e74-835c-4c${++idCounter}`.slice(0, 17);
+ const realId = randomUUID().slice(0, 17);
```

Plus: moved `realIds` into `setupWithRealIds()` so each test gets its
own map. Two reasons: the prior describe-scoped map meant stale
entries from prior tests were visible (rare but possible), and
per-test isolation makes future contributors less likely to write a
fixture that accidentally reads across tests.

The `randomUUID().slice(0, 17)` shape now truly mirrors
`pi-subagents/agent-manager.ts:346`'s production contract — random
prefix, 17 chars, unique per spawn.

### 2. `pi-tasks/test/workflow-handler.test.ts` — async emit + await

```diff
- test("subscribeWorkflow.spawnAgent marks the task active before dispatching", () => {
-   events.emit("workflow:start", startPayload());
-   flush();
+ test("subscribeWorkflow.spawnAgent marks the task active before dispatching", async () => {
+   await events.emit("workflow:start", startPayload());
+   await flush();
```

The cascade is multi-await; awaiting the emit lets the spawn chain
settle before we inspect `spawnAgent.mock.calls`.

### 3. `pi-subagents/test/agent-runner-boundary-survival.test.ts` — `describe.skip` with documentation

The runtime nudge was removed by design; the test pinned the removed
contract. `describe.skip` with a 12-line doc comment explaining the
removal, the replacement mechanism, and how to restore if a future
GC reintroduces the runtime nudge. The `extractStructuredOutputFromFile`
describe block in the same file is unaffected and passes 5/5.

## Behavior change (deliberate)

Zero runtime behavior change. All three fixes are test-only.

- (1) and (2): test fixtures that match production shape correctly.
- (3): skipped obsolete tests with documentation; the replacement
  mechanism (wall-clock deadline + verdict-{task_id}.md file-fallback)
  is the supported wrap-up reminder path per `GC-2026-subagent-time-only-limits`.

## Lessons

1. **Test fixtures mirroring production shorthand need to use the
   same generator.** A counter + slice is not equivalent to
   `randomUUID().slice(0, 17)` — the slice truncation only matters
   when the counter exceeds the slice length. The test passed for the
   first 9 spawns, then failed for the 10th. The "test passes
   locally, fails in CI" pattern that's hard to catch without running
   the full suite in order.

2. **Async event buses need explicit await discipline.** Vitest tests
   commonly use `flush()` (one tick) for sync-feeling async. When the
   chain lengthens (cascade → spawnAgent → store.update), one tick
   stops being enough. Awaiting the emit is the honest answer; flush
   alone is a flaky-test generator.

3. **Source deletions need a test-cleanup PR.** When
   `GC-2026-subagent-time-only-limits` removed `SOFT_LIMIT_STEER_MESSAGE`,
   the test pinning the contract should have been updated in the same
   commit (or immediately after). 48 hours later the test was still
   failing on main and required this GC to clean up.
