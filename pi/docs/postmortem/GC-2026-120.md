## What happened

The Sages task pipeline had three critical gaps when a user typed
`/tasks create "custom task"`:

1. **No auto-decomposition hook.** `/tasks create` never called
   `materializeDecomposeChain`. The user had to switch to chat context
   and wait for the LLM to volunteer decomposition (D6 by design from
   GC-2026-task-feeding-and-decomposition). Tasks without chat-driven
   decomposition sat as planning data indefinitely.

2. **Dead-lock after decomposition.** `materializeDecomposeChain` set
   `T1.blockedBy = [userTask.id]`. The user task had no agent to
   complete it, so T1 could never spawn — the cascade walks only on
   `subagents:completed` events, and there is no completion event for a
   pending user task. The chain was dead-locked from the moment
   decomposition succeeded.

3. **No semantic marker for "intent vs actionable".** Even if a
   reminder mechanism existed, the task itself didn't declare whether
   it needed decomposition. There was no way to distinguish "intent
   awaiting decomposition" from "actionable already dispatched" without
   inspecting `agentType` (which the LLM tool surface didn't
   communicate clearly).

GC-2026-120 formalizes a `kind` semantic (`intent` | `actionable` |
`step`) on user tasks, eliminates the deadlock by auto-completing
`userTask` after successful chain materialization, and adds three
decomposition triggers: inline `--decompose-spec`, deferred
`before_agent_start` reminder, and the existing chat-driven
`decompose_task` tool (kept for backward compatibility).

## Root cause

D6 in the prior GC declared "decomposition is chat-driven by design" —
a single anti-auto-trigger choice that left `/tasks create` disconnected
from the chain pipeline. Combined with `T1.blockedBy = [userTask.id]`
(because the user task was the natural "completion signal" for
decomposition), the result was a hard deadlock with no escape hatch
except manual `TaskUpdate(userTask.id, status: "completed")` — which no
LLM would ever do because the user task had no `agentType` and was
therefore invisible to the feeder.

## Fix

- **D1 — kind semantic**: `TaskStore.create()` now infers `kind` from
  `metadata.created_by` + `agentType`. `intent` is the default for
  user-authored tasks without an agent type; `actionable` is set when
  `agentType` is present; orchestrator-created tasks always carry
  `kind: "step"`.
- **D2 — auto-completion (deadlock fix)**: `materializeDecomposeChain`
  successfully completing now auto-completes the user task with
  `completed_via: "decomposition"`. T1's `blockedBy` was changed from
  `[userTask.id]` to `[]` — T1 is now the chain head with no upstream
  blocker.
- **D3 — three decomposition triggers**: inline `--decompose-spec`,
  deferred `before_agent_start` reminder, and the existing
  chat-driven `decompose_task` tool.
- **D4 — transactional rollback**: `materializeDecomposeChain` is
  wrapped in try/catch. On any failure mid-chain, partial chain tasks
  and the attached reviewer are deleted; the user task is reverted to
  pending if its auto-completion already fired.
- **D5 — abandoned intent reaping**: `AutoClearManager` accepts an
  optional `abandonedIntentHours` (default 0 = disabled). When set,
  pending `kind: "intent"` tasks older than the TTL are auto-deleted
  on `onTurnStart`.
- **D6 — once-per-session reminder**: `before_agent_start` fires a
  single system notification listing pending intent tasks. The flag
  resets on `session_start` so each session gets a fresh nudge.

## What did NOT change

- The D-numbering for `created_by` (still binary: `orchestrator` |
  `user`).
- The cascade semantics in `task-feeder.ts`. Only the userTask
  completion side-effect changed.
- The chat-driven `decompose_task` LLM tool. Backward compat
  preserved.
- The `--decompose` flag in `/tasks create` (rejected per D6 in the
  prior GC; replaced by `--decompose-spec`).
- AGENTS.md / README.md / SKILL.md (deferred to a doc follow-up GC).

## Process notes

The orchestrator's `workflow_run` failed at the entry point with
"extensions not registered" — same environment issue documented in the
GC-2026-task-feeding-and-decomposition postmortem. Per the
soft-mode manual-takeover contract, the orchestrator main agent
implemented all 7 commits directly via `edit` / `write` / `bash` —
bypassing the worktree-dispatch path. The dispatch's "task report"
file path was not relevant here (no subagent was dispatched).

This is the **second** GC the orchestrator has shipped via manual
takeover in this monorepo. The pattern is now established enough to
consider promoting manual takeover to a first-class path for
GCs that touch `pi-tasks` + `pi-orchestrator` together (see Follow-ups).

## Follow-ups

- **Doc GC**: update AGENTS.md / README.md to document `kind` semantics
  and the three decomposition triggers. The user-facing doc still
  treats user tasks as monolithic planning data.
- **Cookbook entry**: a `kind` semantic primer for new contributors
  (`pi/docs/cookbook/kind-intent-actionable-step.md`).
- **Manual takeover formalization**: consider a `manual-takeover`
  workflow_run mode for GCs that touch multiple `pi-*` packages and
  need orchestration across them — saves a round-trip when the
  dispatch path is broken.
- **Decomposition spec ergonomics**: the `T:s|T d;T:s|T d` parser is
  intentionally minimal. A future GC could add a JSON variant or shell
  heredoc support for richer specs.
- **Abandoned intent default TTL**: opt-in by design. A future GC
  could flip the default to 24h after the doc follow-up ships and
  users have had time to opt out.
