## What happened

Originally scoped as a follow-on to `GC-2026-task-feeding-and-decomposition`
that would fix the audit-noted gap: user tasks created via `/tasks create
"<subject>" --agent-type T` sat `pending` forever because no producer ever
called `spawnSubagent` for them. Mid-brainstorm the user reframed the scope
to **option C — full unification**: replace the four parallel cascade
listeners (`workflow-handler.ts` direct spawn + `agentToTask` map,
`decompose-cascade.ts` cascade + `decomposeAgentMap`, `pi-tasks/src/index.ts:227`
TaskExecute cascade + `agentTaskMap`, plus the planned new `user-task-feeder.ts`)
with **one** task-feeder module.

Full unification (Q3=C) was attempted as a single GC. It required
modifying 7+ files in `pi-tasks/src/` and broke 60+ existing test
fixtures that assume the legacy `TaskCreate + TaskExecute` two-step
pattern. Once the producer refactor went in, `TaskCreate` started
auto-spawning via the new feeder, and the followup `TaskExecute` in
those fixtures errored with "not pending". The scope was rolled back
to **Phase 1** (canonical module + unit tests; the producer refactor
deferred to a follow-up GC filed as FU0 in the design doc).

Phase 1 ships:

- `pi-tasks/src/task-feeder.ts` (234 lines) — `registerTaskFeeder`
  factory returning `{ unsubscribe, maybeAutoSpawn }` handle,
  `isFeedableTask` predicate, externally-shared `agentTaskMap` option,
  single `subagents:completed` / `subagents:failed` listener pair.
  Mirrors the `decompose-cascade.ts` pattern.
- `pi-tasks/test/task-feeder.test.ts` (24 cases, all pass) — predicate
  truth table, `maybeAutoSpawn` direct call (eligibility, blockers,
  error handling, idempotency), `subagents:completed` listener
  (map hit/miss, cascade triggering), `subagents:failed` listener
  (stopped vs error), registration (unsub, single map ownership),
  cross-identity non-interference (workflow / decompose / user).
- `pi-tasks/test/auto-cascade.test.ts` deleted (preparation for
  Phase 2; the `cfg.autoCascade` listener itself is unchanged in
  Phase 1 because `pi-tasks/src/index.ts` is unchanged).

`pi-tasks/src/index.ts` is byte-identical to `main` for this commit
(no producers wired in yet). The new module is the canonical
implementation that the four legacy listeners will eventually be
replaced by. Phase 2 owns the producer refactor.

## Why this design

D4 of the prior GC declared "pi-tasks is the sole consumer,
source-agnostic dispatch", but the merged implementation only
realized it for workflow + decompose tasks. The user's mid-brainstorm
reframe to option C was the right architectural call: keeping the
4-way split would have entrenched an `agentId → taskId` lookup that
must check the right map, and a future test or feature would always
have to know which listener owns which task. The unified feeder
collapses the lookup to a single map + a single predicate.

The phased approach is honest about the size of the unification:
the producer refactor touches 60+ test fixtures that need updating
in a focused, reviewable GC. Phase 1 establishes the contract;
Phase 2 swaps the producers.

## What broke / what we had to fix mid-implementation

- **Test fixture (mkTask) put `blockedBy` in metadata instead of the
  Task**. The initial 24-case RED ran with 20/24 pass and 4 fail.
  Two failures (the cascade + the "no cascade" tests) both revealed
  the same root cause: `mkTask`'s override-spread put `blockedBy`
  in the metadata object, not on the Task. The feeder's blocker
  gate read `task.blockedBy ?? []` and saw `[]` — no blockers — so
  it spawned everything. Fix: `mkTask` now calls `store.update(id, {
  addBlockedBy: [...] })` after `store.create` to apply the structural
  field on the task. All 24 pass after the fix.

- **`result: null` vs `result: undefined` in the failure test**. The
  test asserted `result === null` after a real failure, but
  `TaskStore.update` deletes a key set to `null` (per the existing
  comment in `pi-tasks/src/index.ts:286`). The test was wrong
  about the assertion, not the implementation. Updated the test
  expectation to `toBeUndefined()` with a comment explaining the
  store convention.

- **Mid-implementation refactor on the feeder's agentTaskMap**. First
  iteration had the map as a closure inside `registerTaskFeeder`.
  Tests passed, but it would have forced the existing widget /
  `TaskOutput` code in `pi-tasks/src/index.ts` to read from a map
  they don't own. Refactored to `registerTaskFeeder({ agentTaskMap })`
  — the extension factory passes its existing map, the feeder
  populates + consumes it. Tests still pass; the wiring story is
  cleaner for Phase 2.

- **TypeScript: `TaskStore` import path**. Initial import was
  `from "./types.js"`, but `TaskStore` is exported from
  `./task-store.js`. Fixed.

- **TypeScript: `process` global not declared**. The `debugLog`
  helper used `process.env.PI_TASKS_DEBUG` directly. The host
  project doesn't have `@types/node` in `pi-tasks`'s own
  `tsconfig.json` paths, so the reference failed. Switched to
  `globalThis.process?.env?.PI_TASKS_DEBUG` — runtime behavior
  identical, type-clean.

- **Full-unification rollback**. After wiring the 5 producers
  into the feeder (`TaskCreate`, `TaskUpdate`, `TaskExecute`,
  `handleCreateCommand`, plus the planned `materializeDecomposeChain`),
  the test suite went from 0 new failures to 64 new failures.
  60+ of those were fixtures that assumed the old
  `TaskCreate + TaskExecute` two-step pattern. Reverted
  `pi-tasks/src/index.ts` via `git checkout`; the committed diff
  for Phase 1 is +694 / -172 with no `index.ts` changes. The
  design doc's "Why phased" section documents the rollback so
  Phase 2 has explicit scope (AC6-AC12 of the design doc).

## Workflow_run session-runtime mismatch (FU1)

`workflow_run(goal-GC-2026-108.yaml)` hung in this session with the
**same failure mode** as `GC-2026-task-feeding-and-decomposition` §
"Workflow_run session-runtime mismatch":

- `~/.pi/packages/{pi-tasks,pi-subagents}` are installed on disk
- `~/.pi/settings.json` is empty
- `~/.pi/extensions/` does not exist
- `workflow:start` was emitted but no listener caught it
- The Promise stayed pending until harness timeout ("No result
  provided")

Per `AGENTS.md § Orchestrator manual takeover` the main agent
implemented the deliverable directly via `edit` / `write` / `bash`.
This is the **second GC in a row** to hit this same session-runtime
fragility, filed as FU1 in the design doc with two candidate
fixes:

- **FU1a**: `workflow_run` does a final-resort self-registration
  after N seconds of no `workflow:phase-complete` — falls back to
  in-process task creation when the event bus is dead.
- **FU1b**: `pi-orchestrator/scripts/install.sh` becomes atomic +
  adds a post-install smoke test (e.g., emit a `sentinel:ping`
  and verify a `sentinel:pong` from each registered extension
  within 5s).

The fact that **two consecutive GCs have hit the same fragility
without the FU1 GC landing** suggests FU1a / FU1b should be
prioritized over Phase 2 of this GC.
